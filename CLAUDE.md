# Vibeyard contributor guide

Vibeyard is an Electron desktop IDE for seven CLI backends: Claude Code, Codex CLI, GitHub Copilot, Gemini CLI, Pi, Pi-Bolt, and Oh my Pi. Source builds use Node 24 (`.nvmrc`). The published npm launcher accepts Node 18+ and downloads a packaged app.

## Build and checks

```bash
npm install
npm run build
npm test
npx tsc -p tsconfig.renderer.json --noEmit
git diff --check
```

`npm start` builds before launching. There is no hot reload.

Internal working docs (audit status, incident notes, work queue) live in the local-only `todos/` folder — it is gitignored and never committed.

## Current contracts

- [Provider contracts](docs/provider-contracts.md) — registry, profiles, spawn arguments, transcripts and status sources.
- [Session lifecycle](docs/session-lifecycle.md) — PTY exit, title adoption, Kanban sync, persistence and watchers.
- [Security boundaries](docs/security-boundaries.md) — renderer/main boundary, paths, sharing and browser data.
- [Performance and resource limits](docs/performance.md) — search cancellation/cache storage, preview paging, event retention and remaining measurements.
- [UI conventions](docs/ui-conventions.md) — components, widgets, i18n and project layout.
- [Claude hook compatibility](HOOKS.md) — version-specific event payloads and status mapping.
- [Packaging and releases](docs/packaging.md) — artifact matrix, deb build requirements and verification.
- [Feature reference](docs/FEATURES.md) — every feature with behavior, owning module, test mapping, numeric limits and coverage gaps.
- Module-level `Map`/`Set` in `src/main` MUST be capped (exported cap constant + LRU/FIFO eviction per the `fs-utils.ts` idiom), teardown-bound, or transient — enforced by `src/main/module-map-governance.test.ts`; a new collection requires an allowlist entry naming its bound class.

Use `src/main/platform.ts` for OS checks and platform path helpers. Build path expectations with `path.join` or `path.resolve` in tests, including on Windows.

After implementation, review changed code for correctness and unnecessary complexity, run the relevant tests, and update the linked contracts. A change that invalidates a claim in `.claude/skills/*/SKILL.md` updates that skill in the same commit — the skills are executable instructions for future sessions, and a stale one is worse than none (e.g. `add-npm-dependency`'s build gate, `ui-dev`'s component/CSS inventory, `import-legacy-settings`' migration premise). When you add a renderer component, CSS file, provider capability, or packaging step, check whether a skill documents it. `/code-review` and `/simplify` have no definitions in this repository; perform those checks directly when the commands are unavailable. Do not commit, push or create a PR unless requested. `CHANGELOG.md` is generated by the release workflow — edit `.claude/commands/release-notes.md` output only when preparing a local release, and never hand-edit `CHANGELOG.md` by hand on a feature branch.

## Skills

`.claude/skills/` is the single source of repo-maintenance knowledge: `add-npm-dependency`, `import-legacy-settings`, `plan-status-audit`, `ui-dev`, `windows-packaging` (plus the `/commit`, `/release-notes`, `/release` commands in `.claude/commands/`).

Claude Code discovers `.claude/skills/` automatically. Pi and Pi-Bolt do not: `.pi/settings.json` maps the same directory via `"skills": ["../.claude/skills"]`, and project settings load **only after project trust** is granted — an untrusted project loads nothing (`pi-bolt doctor` prints `not trusted (not loaded)`). Verified 2026-10-24: without trust the project skills are absent; with `pi-bolt -a` (trust for one run) all five load. One-off loading, no trust needed: `pi-bolt --skill .claude/skills/<name>`. Do not copy skills into `.pi/skills/` — duplicates drift.

`todos/` (the work queue that `plan-status-audit` reads) is gitignored: on a fresh clone the skill's subject matter does not exist.
