# Release procedure

How a FineVibe version gets from `main` to a user's machine. Two actors, one truth:

- **The Release workflow** (`.github/workflows/release.yml`) is the only thing that
  publishes. It bumps the version, writes the changelog, tags, builds the artifact
  matrix, creates the GitHub Release and publishes the npm launcher.
- **The `/release` command** (`.claude/commands/release.md`) is the local mirror of the
  same steps for an operator who wants the commit/tag made by hand. Its final step pushes
  — and on this fork the push target is `fork`, not `origin` (see "Which remote pushes").

The artifact matrix itself (what each installer is, what is verified on it, the update
feed per target) is specified in [packaging](packaging.md); this doc covers the sequence
and the remote rules.

## 1. The workflow is dispatch-only

`release.yml` triggers on `workflow_dispatch` and nothing else — no `push`, no `tag`, no
release event. Pushing a tag publishes nothing. A release exists only because someone
opened **Actions → Release → Run workflow** and pressed the button.

| Input | Meaning |
|---|---|
| `version` | `patch` \| `minor` \| `major`, or an explicit `X.Y.Z`. Validated against a semver pattern inside the runner before it reaches `npm version` (P2-4); anything else fails the job. |
| `artifacts_only` | Build the matrix from `ref` with **no** bump, tag, push, changelog, GitHub Release, or npm publish. The gate/dry-run leg. |
| `ref` | Branch, tag, or SHA to build when `artifacts_only` is checked (default `main`). |

## 2. Job sequence (`version` run)

1. **`prepare`** — checkout with `fetch-depth: 0`, `npm ci`, `npm test`,
   `npm version <input> --no-git-tag-version`, changelog generated by Claude Code
   (needs the `CLAUDE_KEY` secret) and prepended to `CHANGELOG.md`, release notes
   extracted to an artifact, then `git add package.json package-lock.json CHANGELOG.md`,
   `git commit -m "release: v<version>"`, `git tag -a v<version>`, and the push (see §3).
2. **`build`** (macos-latest) — fails **before** `npm ci` when no complete Apple
   credential set is present (an un-notarized dmg passes codesign and every first launch
   is blocked by Gatekeeper). Builds arm64 + x64 with `--publish never`, verifies the
   committed `build/` icon masters are fresh and byte-match the bundles, deep-codesigns,
   then `stapler validate` + `spctl -a -t install`.
3. **`build-linux`** — deb + AppImage, x64 only. Verifies the deb's control/contents and
   desktop-integration files, and pins the exact AppImage asset name
   `FineVibe-<version>-linux-x86_64.AppImage` (the npm launcher downloads that name).
4. **`build-windows`** — pinned to `windows-2022` (the newer image breaks node-gyp's
   Visual Studio detection for node-pty). Verifies packed native modules target the
   Electron ABI (`scripts/verify-win-exe.mjs`), the exe icon/version resources, and the
   Setup installer identity. **Documented gap (P1-9):** no Authenticode certificate is
   configured, so Windows artifacts ship unsigned.
5. **`publish`** — the ONLY job that creates the GitHub Release (P1-8: the three matrix
   builds used to race the same tag and clobber each other's channel files). Downloads
   every matrix artifact, generates and self-checks `SHA256SUMS.txt`, then
   `gh release create <tag> --verify-assets …`.
6. **`publish-npm`** — strips app dependencies from the manifest copy handed to npm
   (P2-14: the published package is the thin launcher in `bin/finevibe.js`), then
   `npm publish --provenance` on Node 24 (P2-6: the registry publishes who built the
   tarball).

Every build job runs `npm rebuild better-sqlite3` (Node ABI, so the cookie reader is
actually exercised by the tests) and then clears
`node_modules/better-sqlite3/build/Release/.forge-meta` before
`npx electron-builder install-app-deps`, so the packaged bundle carries the Electron ABI
binding.

`artifacts_only` skips steps 1, 5 and 6 entirely and builds the mac leg unsigned
(`CSC_IDENTITY_AUTO_DISCOVERY=false`, `-c.mac.identity=null -c.mac.notarize=false
-c.mac.forceCodeSigning=false`), which is the documented manual exception to the
notarization gate.

## 3. Which remote pushes

The runner's push is correct as written and is not the constraint:

```bash
git push origin main
git push origin "v<version>"
```

Inside a GitHub Actions runner, `origin` is the GitHub repository the workflow runs in
(`leo-3889/finevibe` when dispatched from the fork). On a developer machine in this fork,
`origin` is the **upstream** `elirantutia/vibeyard` checkout URL and pushing it is refused
by the standing fork-rebuild constraint — see
[git history and remote constraints](git-history.md). A hand-run release therefore pushes
to `fork`:

```bash
git push fork main
git push fork "v<version>"
```

Tag naming is the contract between the two actors: `v<version>`, annotated, pointing at
the `release: v<version>` commit that also carries the `CHANGELOG.md` entry. The
auto-updater channels and the per-target update policy are in
[packaging](packaging.md) "Update policy".

## 4. Verifying a published release

From the release assets, in the download directory:

```bash
sha256sum -c SHA256SUMS.txt
```

The npm launcher needs its feed explicitly (it has no baked feed):
`FINEVIBE_RELEASE_REPO=leo-3889/finevibe finevibe`. A packaged app reads the feed baked
into its own `resources/app-update.yml`, which the build pins to this repo's Releases.
Provenance for the launcher: `npm audit signatures` (or the registry's provenance
attestation) must name this repo's release workflow.

`CHANGELOG.md` is generated by the workflow — never hand-edit it on a feature branch;
prepare a local release by editing the `/release-notes` command output only.
