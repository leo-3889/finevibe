# Security boundaries

The renderer sends privileged work through preload and main-process IPC. Validate project paths, including symlinks, before filesystem access. `statusFilePath()` validates UI session IDs before using them as filenames in the hook-status directory under `os.tmpdir()/vibeyard`. A pasted clipboard image crosses the same boundary as bytes only: main generates the filename inside `os.tmpdir()/vibeyard-paste` and allowlists the image formats, so the renderer cannot aim a paste at a path. Clipboard file lists (browser `FileNameW`, `CF_HDROP`, the Finder plist, `text/uri-list`) are read by main and injected as path text only — never written to, and relative names are dropped — so a paste can name files but can never choose a write target.

PTY arguments and environment variables cross a trust boundary. Keep `shell: false`, Windows argument quoting/rejection, and provider-owned environment filtering described in [provider contracts](provider-contracts.md). The embedded webview and Chrome-cookie import handle third-party content and account data; keep browser partitions and permission checks separate from terminal state. Paths a file drop or paste types into a PTY are shell-quoted first (`quoteShellPath` in `src/renderer/components/terminal-utils.ts`): POSIX single quotes with `'` escaped as `'\\''`, Windows double quotes with a trailing `\` doubled so it cannot swallow the closing quote; a Windows path containing `"` is refused there (P1-20) — `\"` is not a literal quote to cmd.exe, it closes the quoted region and leaves everything after it live, the same reason the spawn path rejects quote-bearing arguments — and the pane alert banner names the refused path. Paths with no shell-significant characters pass through unquoted. Unquoted, `My File.pdf` reached the prompt as two arguments every provider reads as two missing files (`9b206f9`).

Chrome-cookie import never touches the user's profile in place. Main copies `Cookies` (and `Login Data`, which nothing reads) into a fresh `os.tmpdir()/vibeyard-chrome-import-<16 hex>` directory (`src/main/chrome-import/copy.ts:27,29-50`), deliberately skipping the WAL/journal sidecars (`copy.ts:12-16`), and the snapshot is removed in a `finally` on every path, decrypt throws included (`src/main/chrome-import/importer.ts:41-87`); the snapshot is opened read-write (`src/main/chrome-import/cookies.ts:54`), so the copy is what keeps Chrome's own store untouched. The renderer names only a profile id: `chromeImport:run` takes `{profileId}` and main resolves it through a containment check that throws `Invalid Chrome profile id` for any id escaping the Chrome user-data root (`src/main/chrome-import/paths.ts:22-31`); only Google Chrome is discovered, from three fixed per-OS user-data paths (`paths.ts:7-19`) — no step accepts a renderer-supplied path. Decryption is per row, and exactly one row class is dropped silently: a Windows `v11` value (Chrome 127+ App-Bound Encryption), counted as `skippedV11` (`src/main/chrome-import/decrypt.ts:34-37`, `cookies.ts:78-81`). Every key-level failure — macOS keychain denial/timeout, a Linux Secret Service lookup failure, any decrypt throw — records its first reason (`cookies.ts:82-92`), is pushed into `ChromeImportResult.errors` (`importer.ts:50`) and makes the run `ok:false` (`importer.ts:91`): a denied keychain can never be reported as an empty success. Plaintext results land in the shared `persist:vibeyard-browser` partition (`importer.ts:52`), the same cookie store the embedded browser uses, and `chromeImport:clearCookies` clears that partition's cookies wholesale, not just the imported rows (`importer.ts:94-97`). Progress is pushed by main on `chromeImport:progress` to the sending webContents only (`src/main/ipc-handlers.ts:900-907`), and there is no cancel channel: dismissing the modal unsubscribes the renderer while main imports to completion (`src/renderer/components/chrome-import-modal.ts:160-170`), so a dismissed import still writes its cookies into that partition.

Renderer-supplied agent file slugs become file names, so `writeAgentFile`/`deleteAgentFile` (`src/main/providers/agent-files.ts`) reject any slug containing path syntax — the allowlist is `[A-Za-z0-9._-]+` — and a crafted slug cannot escape the agent directory (`2db2e70`).

Renderer-supplied branch names become `git checkout` argv entries. `requireValidBranch` (`src/main/git-status.ts`) rejects a non-string, empty, or leading-`-` name before any exec, then runs `git check-ref-format --branch` on the same value, and only then do `checkoutGitBranch`/`createGitBranch` (behind the `git:checkoutBranch` / `git:createBranch` IPC) run `git checkout <name>` / `git checkout -b <name>`. The leading `-` is the concrete risk: git parses it as a checkout flag, not a rev, so a branch spelled `-f` force-discarded the project's uncommitted working tree. `--branch` is the variant that accepts a single-segment name like `main`, and git's own grammar rejects the rest of the shapes that break checkout (`..`, `~`, `^`, `:`, `@{`, control chars, trailing `.`/`/`, `.lock`); every call is `execFile` argv with no shell, so quoting is not a concern.

The repo slug a board pane types steers a `gh api` request made with the user's token. `encodeRepoPath` (`src/main/github-cli.ts`) requires exactly two `owner/name` segments matching `^[A-Za-z0-9][A-Za-z0-9._-]*$` and percent-encodes each segment. `listPullRequests` sends that encoded form as the request path (`repos/<owner>/<name>/pulls`), which also makes a `%2e%2e` (server-side `..`) inert; `listIssues` sends the plain, validated name inside the `q=repo:<owner>/<name>` search qualifier — a qualifier is not a URL path, so there the validation itself is what keeps the value one `repo:` term (the query builder percent-encodes the whole `q` value on the way out). Unvalidated, `repos/../user` is resolved away before the request leaves and reads any endpoint the token can reach, a leading `-` is parsed by gh as a flag, and a space or colon escapes the qualifier into search operators. A rejected slug returns `{ok:false,error:'Invalid repo. Expected owner/name.'}` and never invokes gh.

A `cliSessionId` arrives from the renderer (`session:transcriptExists`, `session:transcriptExistsSync`, `session:exportArchive`, the resume path) and resolves to a path whose existence — and then content — the renderer learns. `TRANSCRIPT_ID_RE` (`src/main/providers/claude-provider.ts`, `src/main/providers/copilot-provider.ts`) is `^(?!\.)[A-Za-z0-9._-]{1,128}$`, and an id outside it returns `null` before any filesystem probe, because those two providers interpolate the id into the path they `existsSync` (Claude `<configDir>/projects/<slug>/<id>.jsonl`, Copilot `~/.copilot/session-state/<id>/events.jsonl`): a `../../x` id was an existence oracle over the whole filesystem. The other providers do not interpolate and are not regex-gated — `getTranscriptPath` in `src/main/providers/pi-provider.ts`, `omp-provider.ts`, `codex-provider.ts` and `gemini-provider.ts` reads the on-disk session directories/filenames and matches the id against those entries (`_<id>.jsonl`, `-<id>.jsonl[.zst]`, `session-…-<shortId>.json`), so a traversal id matches nothing instead of opening a path; Pi/OMP additionally confirm the id from the transcript header (`header.id !== cliSessionId` skips) plus the recorded cwd, and Gemini — whose filename encodes only the first 8 id characters — re-checks the full id inside a bounded head and falls back to the newest candidate when no readable head contains it.

The gate above covers the id the renderer supplies. The id a Pi/OMP transcript *declares* is untrusted input pointing the other way: it is parsed out of a transcript file, becomes that session's `cliSessionId`, and later reaches argv (`--session` / `--resume`) and filename suffixes. `sessionHeaderFromWindow` accepts a header id only inside `COMPATIBLE_SESSION_ID_RE` = `/^[A-Za-z0-9_-]{1,128}$/` (`src/main/providers/pi-compatible-transcripts.ts:373`, applied at `:381`) — wider than a UUIDv7 so a future id format does not break resume, and excluding every character that could break out of a `cmd.exe` argv token (`"`, space, `&`, `|`, `%`, path separators). A header declaring any other id yields no descriptor: the transcript is neither adopted nor offered as resumable.

Destructive app shortcuts do not fire while the user is typing. The shortcut manager suppresses every shortcut except pure view toggles (zoom, panels, help) when the key event targets a real text entry (input, textarea, select, contenteditable) — Ctrl+W mid-rename used to close the session — and a visible modal overlay swallows app shortcuts entirely except zoom and Help, leaving ESC/Enter owned by the dialog. The xterm helper textarea is deliberately not a typing target: terminal panes forward keys to the PTY, so Ctrl+T/Ctrl+W/Ctrl+1-9 keep working inside a terminal (`6af0c7a`).

The main window runs with `nodeIntegration: false`, `contextIsolation: true` and `sandbox: true`; the preload reaches main only through `contextBridge` and sandbox-safe Electron modules, so it cannot import local CommonJS helpers (the zoom bounds are duplicated in `src/preload/preload.ts` for that reason). A `<webview>` guest's privileges are renderer-controlled, so `will-attach-webview` on the main window's host webContents (Electron 41 has no App-level event) pins `nodeIntegration` off, `contextIsolation`/`sandbox` on, and keeps a `preload` only when it is the shipped `browser-tab-preload.js`; destinations stay unrestricted because loading arbitrary remote pages is the feature. Browser-tab webviews set no `allowpopups`, so a guest `window.open()`/`target=_blank` has no attach target and a popup can never inherit a tab's session partition or imported Cookie jar; the renderer-side `new-window` event that used to intercept these was removed by Electron (deprecated v30, gone by v32), making the main-process guest pinning above the only popup backstop. Guest permission request/check handlers are installed by main on the guest's partition session (`session.fromPartition` in `src/main/main.ts`), never by the renderer. The URL bar rejects `javascript:` and `view-source:`.

P2P sharing is opt-in. The host chooses read-only or read-write access; read-write gives the peer terminal command execution. A generated 128-bit share key encrypts connection codes and authenticates the data channel. Do not send scrollback, live output or resize frames before host verification. Treat both the key and codes as sensitive and end a share when the user closes it. The shared pane's right-click menu (Copy / Select all / Paste) follows the negotiated mode: a read-only pane wires Paste to a write function that drops everything, so a viewer's menu can never send input to the host's PTY (`9b206f9`).

Global search writes derived plaintext user text and working directories to `search-index-v2` under Electron user data. Source-path hashes obscure filenames but are not encryption. The index is rebuildable and separate from provider transcripts and the persisted application state. See [performance and resource limits](performance.md) for retention, invalidation and rebuild instructions.

MCP connect URLs are gated in main: `mcpUrlPolicy` (`src/main/mcp-ipc-handlers.ts`) accepts only http/https — every other scheme is rejected — passes exact loopback hosts (`localhost`, `::1`, and the `127.0.0.0/8` literals the URL parser normalizes to), and requires an explicit user confirmation dialog (Cancel default) before any other http(s) connect; an empty URL (stdio-style config) is not gated. The exemption is never a name suffix: the gate performs no DNS, so `*.localhost`, a trailing dot, and IPv4-mapped IPv6 all fall through to confirm — a suffix rule would hand the loopback decision to the resolver/hosts file. Rejections and cancellations surface through the `McpResult.error` channel so the renderer never sits on "Connecting...".

That policy only ever sees the URL the user typed, so `connect` (`src/main/mcp-client.ts`) also pins the connection: `pinnedFetch(new URL(url).host)` is passed as the `fetch` option of both transports (the SSE client when the URL ends in `/sse`, the StreamableHTTP client otherwise). It sets `redirect: 'manual'`, throws on any 3xx response naming the `Location` origin, and re-checks the final response origin against the approved host. The SDK builds its requests with plain `fetch` and the spec default `redirect: 'follow'`, so without this a loopback-exempt endpoint — the no-confirm path — answering `302 -> https://attacker.tld/` would ship the whole MCP handshake and every JSON-RPC payload built from user content to a host no dialog ever named. Refusing the hop beats re-running the confirm dialog for it: an MCP endpoint is one fixed URL, so a real server never needs to change host.

The `mcp:*` write path takes renderer-chosen paths, at both ends. `addMcpServer` (`src/main/claude-cli.ts`) derives `<configDir>/.claude.json` from a `configDir` that arrives verbatim in the `mcp:addServer` args, so a non-empty `configDir` is gated by `isManagedMcpConfigDir`: canonical containment (`canonicalPath` in `src/main/fs-utils.ts`, i.e. `path.resolve` + `realpathSync`) under a stored profile's `configDir` or a known project path from `getKnownProjectPaths()`. `removeMcpServer` gates the echoed `filePath` against a canonical-equality allowlist of the files `getClaudeConfig` lists — `~/.claude.json`, `~/.mcp.json`, `~/.claude/settings.json`, the project's `.mcp.json` / `.claude/settings.json`, and the `configDir`'s `.claude.json` / `.mcp.json` / `settings.json`. Canonical comparison is the point: the renderer spells the same directory with other casing, separators or a junction and `path.resolve` normalizes none of those, so a string compare would silently no-op legitimate deletions while an unvalidated write target is an arbitrary-file-write sink whose payload gets executed — the next CLI launched with that `CLAUDE_CONFIG_DIR` reads the file back as the MCP servers to start. A rejected path throws `Not a writable MCP config path: "<path>"` and the `mcp:addServer` / `mcp:removeServer` handlers map the throw to `{success:false,error}`.

The gates above are covered by unit and integration tests on Windows in this tree; none of them is verified in a running or packaged app. See [audit status](AUDIT_STATUS.md).
