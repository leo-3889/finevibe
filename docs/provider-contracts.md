# Provider contracts

Project context menu → Settings always offers a coding provider and a profile scoped to that provider. `ProjectRecord.defaultProvider` is persisted; absent means the global default. New CLI sessions use explicit override → project default → global default → Claude. Plans and unpinned team chats also prefer an explicit project default over the active tab. Changing the provider resets an incompatible project profile. Running PTYs are not restarted by saving these settings. New-session and board dialogs preselect the project provider.

The registry in `src/main/providers/registry.ts` registers Claude Code, Codex CLI, GitHub Copilot, Gemini CLI, Pi, Pi-Bolt and Oh my Pi. Provider capabilities determine which UI and status paths are enabled; do not assume all providers support profiles, hooks, resume, cost or self titles. `capabilities.hookScope` (default `'user'`) declares where a `hookStatus` provider's hooks live: Copilot is `'project'` (`<project>/.github/hooks/finevibe-copilot-hooks.json`, written at spawn, unlinked at quit), so Preferences → Setup validates it against the active project instead of user scope — with no project open the row is neutral and never counts as an issue (see [FEATURES.md](FEATURES.md) §8 Setup).

`src/main/pty-manager.ts` builds an argv array for node-pty. Never set `shell: true`. On Windows, `resolveWindowsShell` parses npm `.cmd` shims (and extensionless launchers via their `.cmd` sibling) and spawns the shim's real target — `node.exe`/native exe plus its script — directly: cmd.exe ends its command at the first newline and word-splits quoted tokens, which truncated every multi-line startup prompt (Ask AI embeds the selection in code fences) and ran leftover argv fragments as commands. Only for unparseable shims / bare names does the launch fall back to `cmd.exe /c`, where `quoteArgForCmdExe` wraps each token and rejects double quotes that cannot be conveyed safely (tests: `pty-manager.test.ts` §npm shim direct spawn). `partitionUserEnv` (`src/shared/env-vars.ts:137-148`) splits the user's `KEY=VALUE` env into what may be merged over the provider environment and what must not be: the provider-owned keys — `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR`, `PI_CONFIG_DIR`, `PI_PROFILE`, `OMP_PROFILE`, `CLAUDE_IDE_SESSION_ID`, `FINEVIBE_SESSION_ID`, `COPILOT_HOME` (`PROVIDER_OWNED_ENV_KEYS`, `env-vars.ts:72-81`) — are dropped, named on the console with what each one controls and where to set it instead (`providerOwnedEnvReason`, `env-vars.ts:99-106`; `src/main/pty-manager.ts resolveLaunchSpec`), never applied. Matching is `findProviderOwnedEnvKeys` (`env-vars.ts:108-121`) and folds case **only on Windows**: the POSIX child env is case-sensitive, so an inert lowercase variant is neither dropped nor reported (the same S1-08 rule `findConflictingEnvKeys` applies). The New Session modal runs the same finder on the typed env text and refuses the spawn with `tab.newSessionModal.envOwnedError` (`src/renderer/components/tab-bar/session-menu.ts:260-277`) — main's drop is invisible in a packaged app, so a silently ignored variable would leave the user believing it applied; use the Profile field for profile/config-dir intent. `PATH` is deliberately NOT in the list, so a user override of it wins (`env-vars.ts:69-70`, merge at `src/main/pty-manager.ts resolveLaunchSpec`). Raw extra args are tokenized by the shared `tokenizeArgs` (`src/shared/launch-args.ts:26`): space, tab, CR and LF delimit; single quotes are literal content; double quotes honour `\"` and `\\`; an unquoted backslash escapes only a quote or another backslash, so `C:\Users\me` survives unquoted; an unclosed quote consumes the rest of the input; empty arguments (`""`, `''`) are preserved; and tokenizing never throws (`launch-args.ts:9-21`). All seven providers append `tokenizeArgs(opts.extraArgs)` to argv (`claude-provider.ts:118`, `codex-provider.ts buildArgs`, `copilot-provider.ts buildArgs`, `gemini-provider.ts buildArgs`, `pi-provider.ts buildArgs`, `pi-bolt-provider.ts buildArgs`, `omp-provider.ts buildArgs`) — a per-provider whitespace split shipped a quoted value to the CLI as separate arguments. `resolveLaunchSpec` rejects unsupported options before any side effect (`src/main/pty-manager.ts resolveLaunchSpec`): user env keys that move session storage to a root no watcher scans (`UNSUPPORTED_STORAGE_ENV_KEYS` — `PI_CODING_AGENT_SESSION_DIR`, `CODEX_HOME`; `src/shared/launch-args.ts:151-156`, case-folded match `:159-163`), and the extra-arg flags FineVibe owns (`--profile`, `--session`, `--session-id`, `--session-dir`, `--no-session`, `--resume`, `--continue`, `-r`, `-c`, detected in both `--flag x` and `--flag=x` forms; `launch-args.ts:110-120`), checked on the tokenized user args only — never on the flags FineVibe itself adds (`src/main/pty-manager.ts resolveLaunchSpec`). Every hit is reported together in one `LaunchSpecError` (`src/main/pty-manager.ts resolveLaunchSpec`). Launch-argument contracts live in each provider's `buildArgs` and are pinned by its test: Claude passes `--session-id <id>` only in the first-run case (a new session whose CLI session id is already known) and resumes with `-r <id>` (`claude-provider.ts buildArgs`, `claude-provider.test.ts`); Copilot resumes with `--resume=<id>` and carries the queued prompt as `-i <prompt>` — the terminal pane hands the initial prompt to every startup-arg provider, so dropping it on resume silently lost a browser-tab / team / Restart Session prompt delivered to a dormant session (`copilot-provider.ts buildArgs`, `copilot-provider.test.ts`). Gemini carries the same pairing — `-r <id>` then `-i <prompt>`, with the `-i` push deliberately NOT gated on `!isResume` for the same reason (`gemini-provider.ts buildArgs`, `gemini-provider.test.ts` pins `isResume: true`). A rejected `LaunchSpec` does not throw into the IPC caller; it reports through the `pty:exit` channel — see [session lifecycle](session-lifecycle.md). A registry `hostId` on `pty:create` wraps the provider spec instead of spawning it locally (`src/main/pty-manager.ts resolveLaunchSpec`; the legacy free-text `sshHost` wire is retired — the registry record is the only remote spelling): the executable becomes `ssh` and the argv `['-tt', …hostTrustSshArgs(record)… , '-p', <port>, '--', <user>@<host>, <remote command>]` (`src/main/hosts/host-trust.ts hostTrustSshArgs`), with user/host/port taken from the validated record. The remote command is the host's OWN binary path followed by every argv token, each POSIX-quoted (`src/main/pty-manager.ts remoteCommand`): the binary token is `HostRecord.prerequisites[providerId].path` **used verbatim** — no basename is taken and the remote login shell's PATH is never consulted, because the enrollment prereq probe recorded an absolute path on the host (`src/main/pty-manager.ts resolveProviderBinary`). The Windows `.CMD`/`.EXE` shim stem rule is the LOCAL spawn lane only (`src/main/pty-manager.ts resolveWindowsShell`/`resolveCmdShimTarget`); it does not apply to a remote launch. `parseSshHost` (`src/shared/ssh-host.ts`) gates the retired legacy arg; a registry target is gated by `isRegistryHostTarget` (bracketed IPv6 intact). Tests: `pty-manager.test.ts` §resolveLaunchSpec (T2) (golden wrap) + §per-host SSH trust store argv (audit row 35), `ssh-host.test.ts`, `host-trust.test.ts`. System prompts are a spawn-side side effect: `systemPromptArg` (`src/main/launch-session-dir.ts systemPromptArg`) passes the prompt verbatim, EXCEPT a Windows prompt containing a double quote — cmd.exe cannot carry a literal `"`, so the prompt is written to `<sessionDir>/system-prompt.md` (pruned with the launch dir) and passed by path; POSIX, remote (`sshHost`), and quote-free prompts stay inline. **Inline values carry the audit-108 path-spelling guard**: Pi, Pi-Bolt and OMP document `--append-system-prompt` as “Append text **or file contents**”, so a single-line value naming an existing file is silently REPLACED by that file’s contents before the model sees it — a charter that happens to spell a path on the controller (a persona pasted out of a repo, `docs/personas/cmo.md`) ships that file instead of the prompt, with no warning. `systemPromptArg` therefore prepends a newline when the trimmed prompt is an existing file: any value containing a newline is taken as literal text by all three CLIs (verified live on omp/18.15.0 — `omp --append-system-prompt "/tmp/omp spike/quote\"test.md" -p "say ok"` printed the file’s directive `ZISKAPPEND9`; the same value with a leading newline printed `ok`; `strace` shows the `openat` in the first run only; the identical pair of runs on pi-bolt/1.4.0 printed `ZISKAPPEND9` then `ok`, and Pi documents the same “Append text or file contents” flag text). Every other prompt is byte-identical, and the Windows file branch needs no guard (a file’s CONTENTS are appended verbatim, never re-resolved). Cost: one `statSync` per single-line prompt per launch, against the app’s cwd — a RELATIVE-path charter is matched where the app runs, not where the CLI resolves it (absolute spellings, the ones that escape the project, are covered). The stat is LOCAL, so a charter spelling a path that exists only ON THE HOST passes unguarded on a remote (registry-host) launch and the remote CLI performs the substitution — remote charters must not spell host file paths. On Windows a path-spelling prompt routes into the `system-prompt.md` file branch (cmd.exe ends its command at the first newline, so the newline trick would truncate on the `/c` fallback); the guard’s newline prefix is for POSIX/remote lanes only. Claude (`--append-system-prompt`) and Codex (`-c developer_instructions=`) have no file form, so their charter lane is unaffected (and does not route through `systemPromptArg`). Tests: `launch-session-dir.systemprompt.test.ts`. Pi/Pi-Bolt/OMP fresh launches additionally pre-create the transcript header (`seedLaunchTranscript`, `src/main/providers/pi-compatible-transcripts.ts seedLaunchTranscript`, called from each provider's fresh branch — LOCAL launches only, a registry-host launch seeds nothing locally, see Per-host providers) so watcher adoption is deterministic at spawn — the cost: a launch whose CLI never wrote anything (binary missing, spawn rejected) leaves a header-only transcript that surfaces in global search/history until the launch dir is pruned (30 days); status stays neutral (`transcriptStatusFromTail` returns null on a header-only file). Seed header shape is an **accepted limit** (audit 109v): the `version` field is the exported `SEED_SESSION_VERSION` = 3 (Pi’s CURRENT_SESSION_VERSION), not a probed value — the Pi family has no cheap cached version probe (the only probe in the codebase is `claude-version.ts getClaudeVersion`, a 3 s `execSync`), and a spawn per launch on the PTY hot path costs more than the mismatch it prevents: the seed exists only so the CLI’s `--session-id` lookup hits, and today’s CLIs append to a v3 header without migrating it. If the CLI bumps CURRENT_SESSION_VERSION behind a required shape change, bump the constant (pinned by `pi-compatible-transcripts.test.ts §seedLaunchTranscript`).

For profile-aware configuration, follow the same profile resolution chain used by spawning. `provider:getConfig` must receive the selected config directory; Pi reads that directory's `mcp.json`. Do not fall back to a different account's default configuration. `removeProfile` refuses removal while sessions or archives still pin it. The MCP write path is symmetric: `addMcpServer`/`removeMcpServer` take the same config directory, so a profiled project's `claude mcp add`/remove lands in `<configDir>/.claude.json` — never `~/.claude.json`. `removeMcpServer` accepts `filePath` echoed back from the list call, so it writes only to a canonicalized allowlist of known config files (`canonicalPath`, which folds case, separators and junctions); a non-listed target throws `Not a writable MCP config path`. The add side gates the renderer-named dir the same way: `configDir` arrives verbatim in the `mcp:*` IPC args and the write target is derived from it, so `addMcpServer` first runs it through `isManagedMcpConfigDir` — the canonicalized dir must equal, or sit inside, a stored profile's `configDir` or a known project path — and a dir the store never handed out throws `Not a writable MCP config path` naming the derived `<configDir>/.claude.json` before anything is written; `mcp:addServer` surfaces a rejection as `{success:false,error}` (`claude-cli.ts addMcpServer`/`isManagedMcpConfigDir`, `claude-cli.test.ts`).

Transcript lookup must match the requested working directory. A matching CLI session ID in another project is insufficient. The session id a Pi/OMP transcript header declares is untrusted input: `sessionHeaderFromWindow` (`src/main/providers/pi-compatible-transcripts.ts sessionHeaderFromWindow`, gate at `COMPATIBLE_SESSION_ID_RE`) accepts it only inside `COMPATIBLE_SESSION_ID_RE` = `/^[A-Za-z0-9_-]{1,128}$/` — the accepted value becomes the session's `cliSessionId`, later an argv token on the Windows `cmd.exe` spawn path and a filename suffix built from it, so the charset excludes every character that could break out of a token, while staying wider than a UUIDv7 so a future id format does not break resume; a header declaring any other id yields no descriptor, so that transcript is neither adopted nor offered as resumable (see [security boundaries](security-boundaries.md)). Pi/OMP exit reasons come from the same bounded reads: `readSessionExitReasonSync` (`pi-compatible-transcripts.ts readSessionExitReasonSync`) pulls the last 16 KiB (`TAIL_READ_BYTES`, `:70`) and retries once at the 4 MiB cap (`MAX_STATUS_TAIL_BYTES`, `:87`) when that window holds no complete line, and `sessionExitReasonFromTail` (`:281-319`) walks backwards across crash-flush appends only (`tool_execution_start` / `toolResult`, bounded by `MAX_FLUSH_LINES = 32`) — any real user/assistant entry ends the scan, so a marker the CLI resumed past is history, not this launch's exit. Claude, Codex, Copilot and Gemini report status through hooks where supported; Pi and Oh my Pi poll transcripts. See [session lifecycle](session-lifecycle.md) and [hook compatibility](../HOOKS.md).

Pi-Bolt (`pi-bolt`) is the Pi coding agent compiled ahead-of-time to native code — a Pi fork (Pi v1.4.0) with the same on-disk contract: `~/.pi/agent` as its agent dir and Pi's transcript format, only a different binary. Its spawn/env contract mirrors Pi's: every launch pins its own `--session-dir <per-launch dir under the `pi-bolt-sessions` base>` plus `--session-id <pinned id>` on a fresh launch, resumes with `--session <path|id>`, and profiles work via `PI_CODING_AGENT_DIR` (the pinned config dir). Because it shares Pi's tree, Pi-Bolt's global-search corpus is ONLY the launches FineVibe created under `pi-bolt-sessions` — the shared `~/.pi/agent` corpus is enumerated by the Pi provider alone, never double-listed (`pi-bolt-provider.ts discoverTranscripts`, `pi-bolt-provider.test.ts`).

Codex rollouts live under `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<id>.jsonl`; recent Codex builds write zstd-compressed `.jsonl.zst` instead. Indexing and transcript resolution accept both forms — discovery matches `rollout-…-<id>.jsonl` and `.jsonl.zst`, and indexing decompresses a bounded prefix of the compressed file (`32af0b4`). When hooks do not report the CLI session ID, the fallback watcher attributes new rollout files to the tab that launched Codex: registration carries the launch cwd and a rollout is assigned only to a tab registered for the cwd in its `session_meta` line, so an external `codex` run (terminal, CI) no longer hands its transcript to the oldest pending tab. Within one cwd the oldest pending tab pairs with the oldest rollout, and a failed CLI-id write leaves the tab pending with the id unclaimed so the next scan retries; scan-cost pruning and cache bounds are in [session lifecycle](session-lifecycle.md). `codex-provider.cleanup()` calls `stopCodexSessionWatcher()`, so the rollout watcher (a recursive `fs.watch` plus a 2 s poll) is stopped on provider cleanup / quit. Windows status hook commands pin the probed interpreter (`python`, else the `py -3` launcher; see `src/main/prerequisites.ts`) in every generator including `statusCmd`; bare `python` is the App Execution alias on many machines and silently kills every `event:status` hook there (`e866e4a`).

Global search discovery accepts an optional abort signal and stops scheduling work when cancelled. Search indexing shares a four-operation budget and in-flight reads across requests. Workers retain compact results, not the full corpus. A versioned local derived index (`search-index-v3` under Electron user data) reuses unchanged source text after memory-cache eviction; mtime, size and ctime invalidate a record. Deletion pruning runs only after a complete, uncancelled discovery pass: `discoverTranscripts` returns a `TranscriptDiscovery` `{ descriptors, complete, incompleteRoots }` (`src/main/providers/provider.ts:25-29`, contract comment `provider.ts discoverTranscripts`), and a scan root that cannot be listed for any reason other than absence reports incomplete — `ENOENT`/`ENOTDIR` mean missing (`isMissingRootError`, `src/main/providers/transcript-utils.ts:119-122`), every other failure propagates from `readdirForDiscovery` (`:131-142`) and records the root via `TranscriptDiscoveryScan.collect` (`:153-159`). For Claude, Pi and OMP a mid-scan failure drops that root's partial descriptors too: each root's scan returns its list and the list is appended to the corpus only on success (e.g. `claude-provider.ts discoverTranscripts`, `pi-provider.ts discoverTranscripts`); Copilot's only scan failure is the leading root readdir, which precedes every descriptor (`copilot-provider.ts discoverTranscripts`); Codex's tree walk and Gemini's project walk accumulate inline, so their pre-failure descriptors stay in the partial list (`codex-provider.ts discoverTranscripts`, `gemini-provider.ts:271`) — immaterial for deletion, because `pruneSearchIndex` is never fed an incomplete scan: it runs only under `if (!signal?.aborted && discovery.complete)` (`src/main/session-deep-search.ts searchOneProvider`), so derived index entries for an incomplete root's sources are never unlinked (`src/main/session-search-index.ts:62-69`), and each incomplete root is warned once per pass (`src/main/session-deep-search.ts searchOneProvider`). This index contains extracted user text and may be deleted to rebuild it; bump its version when extraction semantics change. Its disk size scales with history, while each text record is capped at 50 Ki characters including join separators and the in-memory text cache has an aggregate budget.

See [performance and resource limits](performance.md) for the exact cache budgets, plaintext disk-index lifecycle, cancellation boundaries, and remaining discovery costs. The four-operation indexing budget is not a global limit for all discovery filesystem work.

## StatusLine consent (settings-guard)

Hooks install without asking; the **statusLine** does not. Overwriting a foreign (non-FineVibe) statusLine command in a config dir requires a recorded consent decision, and every path that writes a statusLine into a dir it does not own — every provider, new ones included — must go through that gate. The contract lives in `src/main/settings-guard.ts` and is documented in full in [HOOKS.md → StatusLine consent](../HOOKS.md); what the provider layer owes it:

- The record is `Preferences.statusLineConsent` + `statusLineConsentCommand` for the default Claude dir, and `statusLineConsentByDir[consentDirKey(dir)]` for every managed profile dir (P1-14) — a provider never reads or writes another dir's record, and `recordDirConsent` is the map's only write site.
- `granted` binds to the exact foreign command it was asked about; a new/unknown foreign command is a new conflict and re-prompts. `declined` freezes the foreign command: `validateSettings` reports fine, and the Setup badge and Fix Settings CTA leave the provider alone (SA-P2-1) — a repair path must never perform the Replace the user declined.
- `settings:reinstall` / `settings:declineStatusLine` gate their `configDir` through `isManagedMcpConfigDir` before touching disk; a `configDir=undefined` decline writes the global record only for the default dir (SA-P3, settings audit).
- Consent is main-owned state: the renderer's whole-state persist load-then-grafts it (SA-P1-1), so a renderer save can never erase a decision made post-load in the boot modal.
- Per-host: the guards stay local-only (a remote session's settings were installed by FineVibe itself) — see Per-host providers above and [security boundaries](security-boundaries.md).

## Per-host providers (Phase 2)

Every provider fact is a fact **about one machine**. `Profile.hostId`, `ProjectRecord.hostId` and `SessionRecord.hostId` carry it (normalized to `'local'` at every load boundary, same idiom as `HostRecord` validation); channels take a trailing optional `hostId` defaulting to `'local'`, so every pre-Phase-2 call site is byte-identical. The spawn plane and the file plane are keyed separately (plan `todos/archives/per-host-providers-plan.md` §2, local-only).

**Spawn plane.** `resolveProviderBinary(providerId, hostId)` (`src/main/pty-manager.ts resolveProviderBinary`): `'local'`/absent → the provider's own `resolveBinaryPath` (PATH/nvm probes, BinaryCache); a registry host → `HostRecord.prerequisites[providerId].path` and **never** local resolution — a missing/never-probed prereq throws a `LaunchSpecError` naming Settings → Hosts. `resolveLaunchSpec`'s registry branch wraps the spec as `ssh -tt <hostTrustSshArgs> -p <port> -- <user>@<host> <remote command>` with user/host/port from the validated record only (gated by `isRegistryHostTarget`, `src/shared/ssh-host.ts` — bracketed IPv6 intact); the remote command is the host prereq path **verbatim** — `remoteCommand` emits `[bin, ...argv]`, so no basename is taken and the remote PATH never resolves the binary — plus POSIX-quoted argv, and the home-relative launch-session-dir token is double-quoted so the remote login shell expands its `~` (`remoteCommand`, `remoteLaunchSessionDir` — one host-side derivation shared by spawn argv and transcript sync, so it works from a Windows controller). A path-shaped resume token is re-anchored under that host dir with its basename kept (`remoteSessionDirArgv`: Pi/Pi-Bolt `--session`, OMP `--resume`), because the provider resolved it against the controller's launch dir and both CLIs read a missing `<path>` as "start this file" — a blank transcript under the pinned id, silently (row 97); a bare id passes through untouched, since the CLIs look it up inside the already-swapped `--session-dir` (tests: `pty-manager.test.ts` §T2 resume cases). `provider:checkBinary(providerId, hostId?)` answers a remote host from the record without probing; a record older than 24h also fires the shared `refreshHostTools` background refresh, gated on connection liveness (a dead connection must not wipe `prerequisites`).

**Pi-compatible launch hooks (`onSessionStarted` / `onSessionResumed`, audit rows 36 + 97).** `pty:create` threads the normalized host id (undefined for a local launch) as the trailing argument of both hooks (`src/main/providers/provider.ts`). A Pi/Pi-Bolt/OMP launch on a registry host therefore creates **no local state at all**: no `ensureLaunchSessionDir`, no `.finevibe.json` sidecar, no `seedLaunchTranscript`, and no local sessions-watcher registration — the transcript lives on the host, and the local watcher would adopt the empty local seed (single-unclaimed-file rule) and mirror a path that can never be written, i.e. a tab with a blank title/status for the session's whole life. The launch's `--session-dir` is `remoteLaunchSessionDir` (the same host-side derivation the spawn argv and the mirror share), published as the pinned CLI id via `writeCliSessionId` and readable by the caller through `getLaunchCliSessionId(sessionId)`, so `pty:create` registers the host-plane sync at spawn — `registerTranscriptSync(…, { sessionDir: <host dir>, hostId })`, mirroring the registration the RESUME branch already made. A REMOTE resume resolves no local path (`getTranscriptPath` is skipped) and argv carries the bare id under the host `--session-dir`; a controller path never reaches the host command. Limit: OMP has no `--session-id` to pin (it generates the id on the host), so a remote **fresh** OMP launch has nothing attributable and keeps its default title/status until it is resumed, where the id is known. Two further remote ceilings are pinned: a remote session's **exit reason** is never read from the controller fs (`isRemoteSyncedSession` gate in the `pty:exit` handler — the generic PTY exit reason is reported instead), and the mirror keeps the **pre-`/clear` file** after a CLI-side `/clear` on the host (the sync lane follows the file it registered, it does not observe host-side clears). Tests: `pi-provider.test.ts` / `pi-bolt-provider.test.ts` / `omp-provider.test.ts` §remote (registry-host) launches, `ipc-handlers.test.ts` §pty:create provider hooks + §pty:exit crash reason (remote skip).

**File plane.** Every provider file read off-box goes through one seam, `readProviderFile` & co. in `src/main/hosts/provider-fs.ts`: local fs for `'local'`, ssh2 sftp for registry hosts. It owns normalization (`normalizeProviderPath`: posix, home-anchored, `..` segments rejected before any disk/network touch), paged window reads (`MAX_WINDOW_BYTES` 1 MiB, `fromEnd` tail reads per [performance](performance.md)), and write (the settings-sync lane). It is deliberately stateless — consumers already gate repeat reads; a second cache adds only staleness. The remote `getConfig` twin (`src/main/hosts/remote-provider-config.ts`) answers pi/pi-bolt `mcp.json` and claude scopes with the host-scope gates: host-scoped project containment and per-host managed-profile `configDir` match. `validateSettings`/`reinstallSettings` (the statusLine guards) stay **local-only**: a remote session's settings were installed by FineVibe itself (enrollment hooks / settings sync), so there is nothing to police.

**Availability + profiles.** The renderer availability cache (`src/renderer/provider-availability.ts`) is keyed by hostId: `'local'` probes binaries, remote hosts hydrate from `hosts:list` prerequisites (no SSH on that path). The New Session provider list, `hasMultipleAvailableProviders` and team-capable filtering scope to the active host tab. `Profile.hostId` rides the same normalization; managed-profile provisioning for a remote host creates `~/.finevibe/profiles/<id>` **on the host** via the exec lane, and `buildEnv` honors the (possibly remote) `configDir` verbatim — the env map is machine-neutral. Remote sessions: status sidecar, transcript sync and lifecycle are in [session lifecycle](session-lifecycle.md); the consent model for the remote lanes is in [security boundaries](security-boundaries.md).

## Plan mode (`planModeArg`)

`planModeArg` is a provider's startup flag for the CLI's native plan mode. Set it ONLY after the exact startup form is observed working on an installed binary — unknown flags make these CLIs exit at startup, bricking every spawn. `buildPlanSessionArgs` (`src/renderer/state/specialized-sessions.ts`) drops plan mode for providers without the flag; `isPlanModeSupported` gates every plan-mode surface — the New Session modal row, the Preferences → General per-provider rows (this matrix at a glance), and the Kanban task modal (disabled + tooltip, never a silently ignored tick) — and `resolvePlanModePreference` turns `Preferences.planModeDefaults` into the quick-send / New-session / Kanban-create default tick (absent = on for plan-capable providers).

| GitHub Copilot | `--mode plan` | Official CLI reference (`--mode=MODE` choices `interactive, plan, autopilot`; `--plan` shorthand) | Enabled |
| Gemini CLI | `--approval-mode=plan` | Official docs (approval mode `plan` = read-only) | Enabled |

Probe results (2026-10-21):

- **Oh my Pi** — `omp --help` (omp/18.12.3) advertises `--plan-yolo`: "Force read-only plan mode at start, auto-approve the plan on the model's first resolve call, then switch to --plan-yolo-into to implement it". ## Project lead charter injection (M1)

A project with `ProjectRecord.lead.enabled` injects its charter into **every** provider launch in that project. The composition is renderer-side and happens at the single spawn choke point — `composeLeadLaunch` (`src/renderer/state/session-factory.ts`, called from `spawnTerminal` in `src/renderer/components/terminal-pane.ts`) — so **main knows nothing about leads**: the charter rides the `systemPrompt` / `initialPrompt` parameters `buildArgs` already transports, through the same quoting lanes as any prompt (`systemPromptArg` for the Windows Pi-compatible file redirect, the POSIX-quoted `ssh` wrap for registry-host launches — remote launches carry the charter verbatim, argv discipline unchanged).

| Provider | Lane the charter rides | argv shape |
|----------|------------------------|------------|
| Claude Code | `systemPrompt` (`systemPromptInjection: true`) | `--append-system-prompt <charter>` |
| Codex CLI | `systemPrompt` | `-c developer_instructions=<charter>` |
| Pi | `systemPrompt` | `--append-system-prompt <charter>` (Windows quote-bearing charters ride the `system-prompt.md` path, `systemPromptArg`) |
| Pi-Bolt | `systemPrompt` | same as Pi (shared `pi-compatible-provider.ts buildArgs`) |
| Oh my Pi | `systemPrompt` | same as Pi — audit row 37 CLOSED: the file-path form is confirmed on omp/18.15.0 (`omp --help`: “Append text or file contents”, plus a live append-and-strace run; `omp-provider.ts` carries the verbatim evidence), so a Windows quote-bearing OMP charter rides the `system-prompt.md` path exactly as Pi/Pi-Bolt’s does. The same confirmation is what makes the path-spelling guard above load-bearing for OMP. |
| GitHub Copilot | `initialPrompt` (`systemPromptInjection: false`) | `-i "[Project lead - <name>]\n<charter>\n[/Project lead]\n\n<prompt>"` |
| Gemini CLI | `initialPrompt` | `-i "<fenced charter>\n\n<prompt>"` |

Rules, pinned by `src/renderer/state/session-factory.test.ts` (argv per provider) and the spawn suite of `src/renderer/components/terminal-pane.test.ts`:

- **Never replaces, always composes.** On the system-prompt lane the charter is the whole value when nothing else flows; when a prompt already flows (a team member's persona, a queued plan prompt) the charter is appended **after** it inside the same parameter, fenced `[Project lead - <name>] … [/Project lead]`. On the initial-prompt lane the fence goes **in front** of the queued prompt.
- **No lane, no prompt, no charter.** Copilot/Gemini have no system-prompt flag, so a launch with no queued prompt carries nothing — pushing the charter alone would make the CLI act on it as a user request. That is a coverage limit of M1, not a bug: such a launch is byte-identical to the pre-feature argv. The same applies to every spawn after the first (Restart Session, crash respawn, window reload): the queued prompt is consumed at the first spawn (`src/renderer/components/terminal-pane.ts` pendingPrompt drain), so a resumed Copilot/Gemini launch carries no charter. The system-prompt lane (Claude/Codex/Pi/Pi-Bolt/OMP) is unaffected — it is recomposed from the project record on every spawn.
- **Zero delta when the feature is off.** No `lead`, `lead.enabled: false`, or a blank charter return both parameters untouched; the argv is byte-identical to the pre-feature launch (pinned per provider).
- **Cap, never truncate — and it gates injection, not the record.** The charter is capped at `LEAD_CHARTER_MAX_BYTES` (4 KiB UTF-8, `src/shared/types.ts`) by the settings dialog; a hand-edited `state.json` charter over the cap makes `composeLeadLaunch` throw naming the size **on the paths that inject**, and the pane surfaces the refusal on the spawn overlay instead of shipping a clipped charter. A no-injection launch (no lane + no queued prompt) never throws — it carries no charter.
- **Windows ceiling: a quote-bearing charter can refuse a cmd-fallback spawn.** The charter rides the existing prompt lanes verbatim; `systemPromptArg` redirects a Windows system prompt containing a double quote into `system-prompt.md` (above), which covers the systemPrompt lane. The initial-prompt-lane prefix (Copilot/Gemini) has no file redirect: on the `cmd.exe /c` fallback `quoteArgForCmdExe` rejects argv containing unrepresentable double quotes, so a charter embedding `"` refuses that spawn (the shim-direct path is unaffected). Operator fix: reword the charter; product fix would be a file redirect for `-i` — not built (ponytail).
- Session-scoped by construction: M2's review spawns and M3's resident lead are separate lanes and are not injected here. Swarm-mode panes are ordinary launches, so they ride the same charter (plan §Injection: "every provider launch in that project").

## On-complete lead review spawn (M2 / I3)

The lead's "accountable" half runs a SECOND, hidden spawn of the project's provider binary per reviewed session (`src/main/lead-review.ts`, `runLeadReview`). It is not a PTY launch and not a tab: `execFile` with the argv array (no shell), the project path as cwd, `stdin` ended immediately (a provider binary on this lane is a TUI, and an interactive CLI handed a prompt through a pipe it never sees closed would sit reading stdin until the timeout kill), `timeout: LEAD_REVIEW_TIMEOUT_MS` with `killSignal: 'SIGKILL'`, and `maxBuffer: LEAD_REVIEW_OUTPUT_MAX_BYTES`.

argv/env come from the SAME `resolveLaunchSpec` a PTY launch uses (`pty-manager.ts`), with `cliSessionId: null`, `isResume: false`, `extraArgs: ''`, `envVars: ''` and the reviewed session's `configDir`, so the profile isolation, session-dir and quoting rules of the table above apply verbatim to the review spawn. A launch the lane refuses (e.g. an unsupported flag combination) is a logged skip, never a crash.

| Slot | Content |
|------|---------|
| `systemPrompt` | `<charter>\n\n` + the digest: `Files touched:\n<paths>` (the existing `git status --porcelain=v2` lane, `getGitFiles(project.path)`, deduped) + `\n\nTranscript tail:\n` (the tail the transcript poller resolved for the reviewed session) |
| `initialPrompt` | the review question: "Review the session per the charter. Reply with exactly one line: VERDICT: APPROVED or VERDICT: FLAGGED, then a one-line summary." |

Rules, pinned by `src/main/lead-review.test.ts`:

- **Only the system-prompt lane.** `systemPromptInjection: true` providers (Claude, Codex, Pi, Pi-Bolt, OMP) are reviewable. Copilot and Gemini have no system-prompt flag, so their spawn would carry the question with no charter — a verdict from a lead that was never told the rules — and the gate skips them with a log line. v1 coverage gap, not a bug.
- **Digest cap `LEAD_REVIEW_DIGEST_MAX_BYTES` (16 KiB UTF-8).** Files list first (whole lines, `…` marks the dropped rest), transcript tail trimmed from the FRONT (newest turns kept); the composed digest never exceeds the cap, so the whole argv argument stays under charter cap + 16 KiB.
- **Local sessions only, one spawn per session ever.** The trigger is the LOCAL transcript-poll status surface (`session-transcript-sync.ts syncEntry`); the remote twin never calls it, and the ledger of reviewed sessions is FIFO-capped (`LEAD_REVIEWED_SESSIONS_MAX`).
- **Verdict text is the contract.** Parsed from stdout+stderr: the newest line matching `^\s*VERDICT:\s*(APPROVED|FLAGGED)` wins (an echoed prompt sits before the answer), summary = rest of that line, else the next non-empty line. Anything unparseable is dropped with one log line — no invented verdicts.
