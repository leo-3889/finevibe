# Provider contracts

Project context menu → Settings always offers a coding provider and a profile scoped to that provider. `ProjectRecord.defaultProvider` is persisted; absent means the global default. New CLI sessions use explicit override → project default → global default → Claude. Plans and unpinned team chats also prefer an explicit project default over the active tab. Changing the provider resets an incompatible project profile. Running PTYs are not restarted by saving these settings. New-session and board dialogs preselect the project provider.

The registry in `src/main/providers/registry.ts` registers Claude Code, Codex CLI, GitHub Copilot, Gemini CLI, Pi, Pi-Bolt and Oh my Pi. Provider capabilities determine which UI and status paths are enabled; do not assume all providers support profiles, hooks, resume, cost or self titles. `capabilities.hookScope` (default `'user'`) declares where a `hookStatus` provider's hooks live: Copilot is `'project'` (`<project>/.github/hooks/finevibe-copilot-hooks.json`, written at spawn, unlinked at quit), so Preferences → Setup validates it against the active project instead of user scope — with no project open the row is neutral and never counts as an issue (see [FEATURES.md](FEATURES.md) §8 Setup).

`src/main/pty-manager.ts` builds an argv array for node-pty. Never set `shell: true`. On Windows, `quoteArgForCmdExe` wraps each `cmd.exe` token and rejects double quotes that cannot be conveyed safely. `partitionUserEnv` (`src/shared/env-vars.ts:137-148`) splits the user's `KEY=VALUE` env into what may be merged over the provider environment and what must not be: the provider-owned keys — `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR`, `PI_CONFIG_DIR`, `PI_PROFILE`, `OMP_PROFILE`, `CLAUDE_IDE_SESSION_ID`, `FINEVIBE_SESSION_ID`, `COPILOT_HOME` (`PROVIDER_OWNED_ENV_KEYS`, `env-vars.ts:72-81`) — are dropped, named on the console with what each one controls and where to set it instead (`providerOwnedEnvReason`, `env-vars.ts:99-106`; `src/main/pty-manager.ts:454-461`), never applied. Matching is `findProviderOwnedEnvKeys` (`env-vars.ts:108-121`) and folds case **only on Windows**: the POSIX child env is case-sensitive, so an inert lowercase variant is neither dropped nor reported (the same S1-08 rule `findConflictingEnvKeys` applies). The New Session modal runs the same finder on the typed env text and refuses the spawn with `tab.newSessionModal.envOwnedError` (`src/renderer/components/tab-bar/session-menu.ts:260-277`) — main's drop is invisible in a packaged app, so a silently ignored variable would leave the user believing it applied; use the Profile field for profile/config-dir intent. `PATH` is deliberately NOT in the list, so a user override of it wins (`env-vars.ts:69-70`, merge at `src/main/pty-manager.ts:462`). Raw extra args are tokenized by the shared `tokenizeArgs` (`src/shared/launch-args.ts:26`): space, tab, CR and LF delimit; single quotes are literal content; double quotes honour `\"` and `\\`; an unquoted backslash escapes only a quote or another backslash, so `C:\Users\me` survives unquoted; an unclosed quote consumes the rest of the input; empty arguments (`""`, `''`) are preserved; and tokenizing never throws (`launch-args.ts:9-21`). All seven providers append `tokenizeArgs(opts.extraArgs)` to argv (`claude-provider.ts:118`, `codex-provider.ts:80`, `copilot-provider.ts:81`, `gemini-provider.ts:118`, `pi-provider.ts:104`, `pi-bolt-provider.ts:125`, `omp-provider.ts:98`) — a per-provider whitespace split shipped a quoted value to the CLI as separate arguments. `resolveLaunchSpec` rejects unsupported options before any side effect (`src/main/pty-manager.ts:293-341`): user env keys that move session storage to a root no watcher scans (`UNSUPPORTED_STORAGE_ENV_KEYS` — `PI_CODING_AGENT_SESSION_DIR`, `CODEX_HOME`; `src/shared/launch-args.ts:151-156`, case-folded match `:159-163`), and the extra-arg flags FineVibe owns (`--profile`, `--session`, `--session-id`, `--session-dir`, `--no-session`, `--resume`, `--continue`, `-r`, `-c`, detected in both `--flag x` and `--flag=x` forms; `launch-args.ts:110-120`), checked on the tokenized user args only — never on the flags FineVibe itself adds (`src/main/pty-manager.ts:330-334`). Every hit is reported together in one `LaunchSpecError` (`src/main/pty-manager.ts:336-341`). Launch-argument contracts live in each provider's `buildArgs` and are pinned by its test: Claude passes `--session-id <id>` only in the first-run case (a new session whose CLI session id is already known) and resumes with `-r <id>` (`claude-provider.ts buildArgs`, `claude-provider.test.ts`); Copilot resumes with `--resume=<id>` and carries the queued prompt as `-i <prompt>` — the terminal pane hands the initial prompt to every startup-arg provider, so dropping it on resume silently lost a browser-tab / team / Restart Session prompt delivered to a dormant session (`copilot-provider.ts buildArgs`, `copilot-provider.test.ts`). A rejected `LaunchSpec` does not throw into the IPC caller; it reports through the `pty:exit` channel — see [session lifecycle](session-lifecycle.md). An `sshHost` on `pty:create` wraps the provider spec instead of spawning it locally: the executable becomes `ssh` and the argv `['-tt', '--', <host>, <remote command>]`, where the remote command is the provider binary's basename plus POSIX-quoted argv (the remote login shell's PATH resolves the remote's own install; the Windows `.CMD`/`.EXE` shim stem is the POSIX command). The value passes `parseSshHost` (`src/shared/ssh-host.ts`) before it reaches argv — the same gate as the UI field, since the renderer string is untrusted. Tests: `pty-manager.test.ts` (wrap), `ssh-host.test.ts`.

For profile-aware configuration, follow the same profile resolution chain used by spawning. `provider:getConfig` must receive the selected config directory; Pi reads that directory's `mcp.json`. Do not fall back to a different account's default configuration. `removeProfile` refuses removal while sessions or archives still pin it. The MCP write path is symmetric: `addMcpServer`/`removeMcpServer` take the same config directory, so a profiled project's `claude mcp add`/remove lands in `<configDir>/.claude.json` — never `~/.claude.json`. `removeMcpServer` accepts `filePath` echoed back from the list call, so it writes only to a canonicalized allowlist of known config files (`canonicalPath`, which folds case, separators and junctions); a non-listed target throws `Not a writable MCP config path`. The add side gates the renderer-named dir the same way: `configDir` arrives verbatim in the `mcp:*` IPC args and the write target is derived from it, so `addMcpServer` first runs it through `isManagedMcpConfigDir` — the canonicalized dir must equal, or sit inside, a stored profile's `configDir` or a known project path — and a dir the store never handed out throws `Not a writable MCP config path` naming the derived `<configDir>/.claude.json` before anything is written; `mcp:addServer` surfaces a rejection as `{success:false,error}` (`claude-cli.ts addMcpServer`/`isManagedMcpConfigDir`, `claude-cli.test.ts`).

Transcript lookup must match the requested working directory. A matching CLI session ID in another project is insufficient. The session id a Pi/OMP transcript header declares is untrusted input: `sessionHeaderFromWindow` (`src/main/providers/pi-compatible-transcripts.ts:380`, gate at `:385`) accepts it only inside `COMPATIBLE_SESSION_ID_RE` = `/^[A-Za-z0-9_-]{1,128}$/` (`:377`) — the accepted value becomes the session's `cliSessionId`, later an argv token on the Windows `cmd.exe` spawn path and a filename suffix built from it, so the charset excludes every character that could break out of a token, while staying wider than a UUIDv7 so a future id format does not break resume; a header declaring any other id yields no descriptor, so that transcript is neither adopted nor offered as resumable (see [security boundaries](security-boundaries.md)). Pi/OMP exit reasons come from the same bounded reads: `readSessionExitReasonSync` (`pi-compatible-transcripts.ts:326-338`) pulls the last 16 KiB (`TAIL_READ_BYTES`, `:70`) and retries once at the 4 MiB cap (`MAX_STATUS_TAIL_BYTES`, `:87`) when that window holds no complete line, and `sessionExitReasonFromTail` (`:281-319`) walks backwards across crash-flush appends only (`tool_execution_start` / `toolResult`, bounded by `MAX_FLUSH_LINES = 32`, `:285`) — any real user/assistant entry ends the scan, so a marker the CLI resumed past is history, not this launch's exit. Claude, Codex, Copilot and Gemini report status through hooks where supported; Pi and Oh my Pi poll transcripts. See [session lifecycle](session-lifecycle.md) and [hook compatibility](../HOOKS.md).

Pi-Bolt (`pi-bolt`) is the Pi coding agent compiled ahead-of-time to native code — a Pi fork (Pi v1.4.0) with the same on-disk contract: `~/.pi/agent` as its agent dir and Pi's transcript format, only a different binary. Its spawn/env contract mirrors Pi's: every launch pins its own `--session-dir <per-launch dir under the `pi-bolt-sessions` base>` plus `--session-id <pinned id>` on a fresh launch, resumes with `--session <path|id>`, and profiles work via `PI_CODING_AGENT_DIR` (the pinned config dir). Because it shares Pi's tree, Pi-Bolt's global-search corpus is ONLY the launches FineVibe created under `pi-bolt-sessions` — the shared `~/.pi/agent` corpus is enumerated by the Pi provider alone, never double-listed (`pi-bolt-provider.ts discoverTranscripts`, `pi-bolt-provider.test.ts`).

Codex rollouts live under `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<id>.jsonl`; recent Codex builds write zstd-compressed `.jsonl.zst` instead. Indexing and transcript resolution accept both forms — discovery matches `rollout-…-<id>.jsonl` and `.jsonl.zst`, and indexing decompresses a bounded prefix of the compressed file (`32af0b4`). When hooks do not report the CLI session ID, the fallback watcher attributes new rollout files to the tab that launched Codex: registration carries the launch cwd and a rollout is assigned only to a tab registered for the cwd in its `session_meta` line, so an external `codex` run (terminal, CI) no longer hands its transcript to the oldest pending tab. Within one cwd the oldest pending tab pairs with the oldest rollout, and a failed CLI-id write leaves the tab pending with the id unclaimed so the next scan retries; scan-cost pruning and cache bounds are in [session lifecycle](session-lifecycle.md). `codex-provider.cleanup()` calls `stopCodexSessionWatcher()`, so the rollout watcher (a recursive `fs.watch` plus a 2 s poll) is stopped on provider cleanup / quit. Windows status hook commands pin the probed interpreter (`python`, else the `py -3` launcher; see `src/main/prerequisites.ts`) in every generator including `statusCmd`; bare `python` is the App Execution alias on many machines and silently kills every `event:status` hook there (`e866e4a`).

Global search discovery accepts an optional abort signal and stops scheduling work when cancelled. Search indexing shares a four-operation budget and in-flight reads across requests. Workers retain compact results, not the full corpus. A versioned local derived index (`search-index-v3` under Electron user data) reuses unchanged source text after memory-cache eviction; mtime, size and ctime invalidate a record. Deletion pruning runs only after a complete, uncancelled discovery pass: `discoverTranscripts` returns a `TranscriptDiscovery` `{ descriptors, complete, incompleteRoots }` (`src/main/providers/provider.ts:25-29`, contract comment `:54-62`), and a scan root that cannot be listed for any reason other than absence reports incomplete — `ENOENT`/`ENOTDIR` mean missing (`isMissingRootError`, `src/main/providers/transcript-utils.ts:119-122`), every other failure propagates from `readdirForDiscovery` (`:131-142`) and records the root via `TranscriptDiscoveryScan.collect` (`:153-159`). For Claude, Pi and OMP a mid-scan failure drops that root's partial descriptors too: each root's scan returns its list and the list is appended to the corpus only on success (e.g. `claude-provider.ts:186-188`, `pi-provider.ts:250-251`); Copilot's only scan failure is the leading root readdir, which precedes every descriptor (`copilot-provider.ts:148-149`); Codex's tree walk and Gemini's project walk accumulate inline, so their pre-failure descriptors stay in the partial list (`codex-provider.ts:219`, `gemini-provider.ts:271`) — immaterial for deletion, because `pruneSearchIndex` is never fed an incomplete scan: it runs only under `if (!signal?.aborted && discovery.complete)` (`src/main/session-deep-search.ts:242-244`), so derived index entries for an incomplete root's sources are never unlinked (`src/main/session-search-index.ts:62-69`), and each incomplete root is warned once per pass (`src/main/session-deep-search.ts:239-241`). This index contains extracted user text and may be deleted to rebuild it; bump its version when extraction semantics change. Its disk size scales with history, while each text record is capped at 50 Ki characters including join separators and the in-memory text cache has an aggregate budget.

See [performance and resource limits](performance.md) for the exact cache budgets, plaintext disk-index lifecycle, cancellation boundaries, and remaining discovery costs. The four-operation indexing budget is not a global limit for all discovery filesystem work.

## StatusLine consent (settings-guard)

Hooks install without asking; the **statusLine** does not. Overwriting a foreign (non-FineVibe) statusLine command in a config dir requires a recorded consent decision, and every path that writes a statusLine into a dir it does not own — every provider, new ones included — must go through that gate. The contract lives in `src/main/settings-guard.ts` and is documented in full in [HOOKS.md → StatusLine consent](../HOOKS.md); what the provider layer owes it:

- The record is `Preferences.statusLineConsent` + `statusLineConsentCommand` for the default Claude dir, and `statusLineConsentByDir[consentDirKey(dir)]` for every managed profile dir (P1-14) — a provider never reads or writes another dir's record, and `recordDirConsent` is the map's only write site.
- `granted` binds to the exact foreign command it was asked about; a new/unknown foreign command is a new conflict and re-prompts. `declined` freezes the foreign command: `validateSettings` reports fine, and the Setup badge and Fix Settings CTA leave the provider alone (SA-P2-1) — a repair path must never perform the Replace the user declined.
- `settings:reinstall` / `settings:declineStatusLine` gate their `configDir` through `isManagedMcpConfigDir` before touching disk; a `configDir=undefined` decline writes the global record only for the default dir (SA-P3, settings audit).
- Consent is main-owned state: the renderer's whole-state persist load-then-grafts it (SA-P1-1), so a renderer save can never erase a decision made post-load in the boot modal.
- Per-host: the guards stay local-only (a remote session's settings were installed by FineVibe itself) — see Per-host providers above and [security boundaries](security-boundaries.md).

## Per-host providers (Phase 2)

Every provider fact is a fact **about one machine**. `Profile.hostId`, `ProjectRecord.hostId` and `SessionRecord.hostId` carry it (normalized to `'local'` at every load boundary, same idiom as `HostRecord` validation); channels take a trailing optional `hostId` defaulting to `'local'`, so every pre-Phase-2 call site is byte-identical. The spawn plane and the file plane are keyed separately (plan `todos/archives/per-host-providers-plan.md` §2, local-only).

**Spawn plane.** `resolveProviderBinary(providerId, hostId)` (`src/main/pty-manager.ts:413`): `'local'`/absent → the provider's own `resolveBinaryPath` (PATH/nvm probes, BinaryCache); a registry host → `HostRecord.prerequisites[providerId].path` and **never** local resolution — a missing/never-probed prereq throws a `LaunchSpecError` naming Settings → Hosts. `resolveLaunchSpec`'s registry branch (`:598`) wraps the spec as `ssh -tt -p <port> -- <user>@<host> <remote command>` with user/host/port from the validated record only (gated by `isRegistryHostTarget`, `src/shared/ssh-host.ts` — bracketed IPv6 intact); the remote command is the binary basename plus POSIX-quoted argv, and the home-relative launch-session-dir token is double-quoted so the remote login shell expands its `~` (`remoteCommand`, `remoteLaunchSessionDir` — one host-side derivation shared by spawn argv and transcript sync, so it works from a Windows controller). `provider:checkBinary(providerId, hostId?)` answers a remote host from the record without probing; a record older than 24h also fires the shared `refreshHostTools` background refresh, gated on connection liveness (a dead connection must not wipe `prerequisites`).

**File plane.** Every provider file read off-box goes through one seam, `readProviderFile` & co. in `src/main/hosts/provider-fs.ts`: local fs for `'local'`, ssh2 sftp for registry hosts. It owns normalization (`normalizeProviderPath`: posix, home-anchored, `..` segments rejected before any disk/network touch), paged window reads (`MAX_WINDOW_BYTES` 1 MiB, `fromEnd` tail reads per [performance](performance.md)), and write (the settings-sync lane). It is deliberately stateless — consumers already gate repeat reads; a second cache adds only staleness. The remote `getConfig` twin (`src/main/hosts/remote-provider-config.ts`) answers pi/pi-bolt `mcp.json` and claude scopes with the host-scope gates: host-scoped project containment and per-host managed-profile `configDir` match. `validateSettings`/`reinstallSettings` (the statusLine guards) stay **local-only**: a remote session's settings were installed by FineVibe itself (enrollment hooks / settings sync), so there is nothing to police.

**Availability + profiles.** The renderer availability cache (`src/renderer/provider-availability.ts`) is keyed by hostId: `'local'` probes binaries, remote hosts hydrate from `hosts:list` prerequisites (no SSH on that path). The New Session provider list, `hasMultipleAvailableProviders` and team-capable filtering scope to the active host tab. `Profile.hostId` rides the same normalization; managed-profile provisioning for a remote host creates `~/.finevibe/profiles/<id>` **on the host** via the exec lane, and `buildEnv` honors the (possibly remote) `configDir` verbatim — the env map is machine-neutral. Remote sessions: status sidecar, transcript sync and lifecycle are in [session lifecycle](session-lifecycle.md); the consent model for the remote lanes is in [security boundaries](security-boundaries.md).

## Plan mode (`planModeArg`)

`planModeArg` is a provider's startup flag for the CLI's native plan mode. Set it ONLY after the exact startup form is observed working on an installed binary — unknown flags make these CLIs exit at startup, bricking every spawn. `buildPlanSessionArgs` (`src/renderer/state/specialized-sessions.ts`) drops plan mode for providers without the flag; `isPlanModeSupported` gates every plan-mode surface — the New Session modal row, the Preferences → General per-provider rows (this matrix at a glance), and the Kanban task modal (disabled + tooltip, never a silently ignored tick) — and `resolvePlanModePreference` turns `Preferences.planModeDefaults` into the quick-send / New-session / Kanban-create default tick (absent = on for plan-capable providers).

| Provider | `planModeArg` | Verified against | Status |
|----------|---------------|------------------|--------|
| Claude Code | `--permission-mode plan` | Claude Code docs | Enabled |
| GitHub Copilot | `--mode plan` | Official CLI reference (`--mode=MODE` choices `interactive, plan, autopilot`; `--plan` shorthand) | Enabled |
| Gemini CLI | `--approval-mode=plan` | Official docs (approval mode `plan` = read-only) | Enabled |
| Codex CLI | — (unset) | Not probed — CLI not installed on 2026-10-21 | VERIFICATION-PENDING |
| Pi | — (never) | Author's explicit non-goal (pi-mono blog + README): "pi does not and will not have a built-in plan mode" | Permanent non-support |
| Pi-Bolt | — (never) | Pi fork (Pi v1.4.0) — inherits the author's explicit non-goal verbatim | Permanent non-support |
| Oh my Pi | `--plan-yolo` | omp/18.12.3 live binary, 2026-10-21 | Enabled |

Probe results (2026-10-21):

- **Oh my Pi** — `omp --help` (omp/18.12.3) advertises `--plan-yolo`: "Force read-only plan mode at start, auto-approve the plan on the model's first resolve call, then switch to --plan-yolo-into to implement it". A live spawn confirmed enforcement: a write-tool request was refused ("Plan mode is active… the write tool is restricted to `local://` planning artifacts") and no file was created. omp exits on unknown flags (`--definitely-not-a-flag` → `Error: unknown flag`), so flag acceptance is proof of existence. Traps: `--plan <model>` selects the plan-role model, NOT plan mode; the handoff target `--plan-yolo-into` (default the `@smol` role) must have auth at startup, else the spawn exits (`error: No API key for …`); `--config` takes an overlay FILE path, not inline `key=value`; `plan.defaultOnStartup` (boolean, default `false`, verified via `omp config get`) backs the config-dir fallback route.
- **Codex CLI** — plan mode is GA (rust-v0.94.0 collaboration mode; TUI `/plan` / Shift+Tab), but `--collaboration-mode` exists only on `codex exec` (headless JSON, incompatible with FineVibe's PTY terminal), there is no TUI startup parameter (openai/codex#13377 — the startup config field is removed on main), and the binary is not installed here, so the probe never ran: the flag stays UNSET. A future probe that finds a startup form sets `planModeArg`; if none exists, the fallback is startup `/plan` PTY input (`planModeStartupInput` capability — its own plan).
