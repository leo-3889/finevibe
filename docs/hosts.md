# Hosts (multi-host SSH)

FineVibe enrolls remote SSH hosts (Settings → Hosts), runs interactive shells on them, and — since Phase 2 (`todos/archives/per-host-providers-plan.md`, local-only) — runs coding-tool sessions, provider file reads, settings sync, and the Add-project verbs on them. Host-keyed provider behavior is in [provider contracts](provider-contracts.md); remote session status/transcripts in [session lifecycle](session-lifecycle.md).

## Coherence principle (owner-ratified 2026-10-26)

**Never silently lie.** For any remote-scope target (a host tab, a remote project, a remote session), every control must be exactly one of:

- **(a) host-aware** — it operates against that host;
- **(b) hidden** — the control is absent in remote scope (the host chip names the scope);
- **(c) explicit-local** — one visible line says "this machine" and names the remote target where relevant.

A silent local fallback on a remote-scope target — local git shown for a remote repo, local files in quick-open, a local profile offered to a remote session — is a **bug**, not a limitation: the user cannot distinguish "the host has nothing" from "FineVibe looked in the wrong machine". This rule binds every current and future feature; enforcement phases are tracked in `todos/archives/audits-2026-10-26/HOST_INTEGRATION_COHERENCE_2026-10-26.md` (local).

Enforcement status — **Phase 1 (profiles)**: the Profiles section edits ONE host at a time (scope select drives list, defaults, Add-form); new-session/project pickers offer only launch-host profiles; `defaultProfiles` keys are `<hostId>|<providerId>` (bare key = local, zero migration, no cross-host inheritance); `resolveProfile` drops pins whose profile lives on another machine (`src/shared/profile-keys.ts`). **Phase 2 (Setup)**: a scope select (= `Preferences.activeHostId`, the sidebar's own control) chooses the machine; remote scope probes binaries via `provider:checkBinary(id, hostId)`, never runs local statusline/hooks validation (Settings-sync tiers shown instead), un-enrolled hosts get an enroll-first row, missing binary offers Re-check — the Setup badge stays local (app readiness). Phase 3 (git/quick-open/storage explicit states) follows. **Phase 3 (silent lies)**: git panel + quick-open render explicit remote-scope states naming the host (no local scan, no "clean tree"/"No files found" lies); `git-status.ts` skips polling/watching remote projects and drops their caches; main-side belt (`ipc-handlers.ts remoteProjectOwnerOf`, `store.getRemoteProjectRoots`) refuses remote-project-rooted cwds on every `git:*` channel (`requireGitRoot`) and `fs:listFiles`, with greppable `blocked: … remote host` log lines. Storage section needs nothing (it sizes userData subtrees only). The read-only remote git panel over the exec lane is the owner-promised next task.

## Host-first-class architecture (owner-ratified 2026-10-26)

The coding tools are scoped to hosts; the architecture must reflect that — **host is a dimension of the contract, not a bolt-on parameter**. Binding rules for every provider-plane capability:

- **R1 — operation contract.** Every provider-plane operation is shaped `(hostId, providerId, …)`. Local is a VALUE of `hostId`, never the parameter-less code path. Wire formats may keep trailing-optional `hostId` for compatibility (Local wire byte-identical), but module APIs take the host explicitly.
- **R2 — sibling lanes.** Each host-routed capability is one lane abstraction with one signature: `execOn(hostId)` / `fsOn(hostId)` / `gitOn(hostId)` — the LOCAL implementation (child_process, fs, local git) is a SIBLING selected by hostId, never a fallback that remote degrades into. Existing instances: `remote-fs.ts` rails, `checkBinary(id, hostId)`, `profiles:provision`. Retrofit backlog: `git:*` channels (Phase 3.5 — the read-only remote git panel IS `gitOn(hostId)`: status/diff over the exec lane, local git behind the same signature; the refuse-bolt retires), then `fs:listFiles` (sftp walk).
- **R3 — host-scoped gates.** Path containment is evaluated against THAT host's project records (posix for remote), never by canonicalizing a remote string on the local filesystem — phantom-path equality is the shared-fiction bug the Phase 3 belt patches. The launch gate's host-aware form is the Phase 0 acceptance contract (concurrent lane).
- **R4 — host-scoped identity.** Profiles, config dirs, project roots and default-profile keys belong to exactly one host (`src/shared/profile-keys.ts`); pickers filter by host, resolvers (`resolveProfile`, `resolvePinnedTeamProfile`) drop cross-host pins at launch scope.

Per-operation scoping matrix (2026-10-26, audit §6):

| Plane | Host-scoped | Local-only (belt-refused / tiered per the coherence principle) |
|---|---|---|
| Runtime: spawn, shell, `checkBinary` (7/7), status sidecars, transcripts, Add-project verbs, profile provision | ✅ via SSH lanes (spawn hostId = Phase 0 lane, in flight) | — |
| FS rails: `listDir`/`readFile`/`stat`/`exists`/`isDirectory` | ✅ `remote-fs.ts` siblings | — (`fs:listFiles` R2 retrofit landed: sftp walk, Phase 4a) |
| Config plane: settings sync 7/7, `getConfig` 7/7 | ✅ (Phase 4c: codex/copilot/gemini twins + file sets joined pi/pi-bolt/omp/claude) | hooks/statusline validation (Setup tier, sync-routed) |
| Git: status/files/diff/worktrees/branches | 7/7 `gitOn(hostId)` — reads (Phase 3.5) + write-side stage/unstage/discard/checkout/create (Phase 4b) | — (refuse-belt retired) |

## Registry

`HostRecord` (`src/shared/types.ts`) lives in `PersistedState.hosts` (`src/main/store.ts`). Every load path (`loadState`, `saveState`, `saveStateSync`, `defaultState`) normalizes the array through `validateHostRecordShape` (`src/shared/ssh-host.ts`): entries that are not objects, miss required fields, carry an out-of-range port, or hold a non-POSIX `defaultFolder` are dropped, never repaired. The renderer hydrates the same shape (`hydrateLoadedState`, `src/renderer/state/persistence.ts`) but never writes hosts directly — all mutations go through `hosts:*` IPC into `src/main/hosts/host-registry.ts` (create/update/delete; create honors a draft `id` so a pre-generated keypair directory matches its host). That boundary is enforced main-side, not just by convention (rows 31/34 bypass): the renderer persists the WHOLE state including `hosts` (`store:save` / `store:save-sync`), so `graftMainOwnedHosts` (`src/main/store.ts`, the S1-02 `windowBounds`/consent idiom) re-asserts the main-owned fields from the cache on every write — `enrollmentStatus`, the probe/pin fields, `managedKey` DERIVED from the stored-or-gated path, and a `privateKeyPath` that must pass the same `isRendererKeyPathAllowed` containment `hosts:update` applies (a path outside `<userData>/hosts/` + `~/.ssh` keeps the stored value). An id main never created is kept but starts `draft`, unpinned and unprobed, so a forged `enrolled` cannot skip the state machine and a forged `managedKey` cannot make `deleteHost` unlink a foreign key.

`hosts:update` is a field **allowlist** (`HOST_EDITABLE_FIELDS`, `src/main/ipc/hosts-domains.ts`; row 31): `name`, `user`, `host`, `port`, `authKind`, `color`, `privateKeyPath`, `defaultFolder`, `settingsSync` — the edit form's own set. Everything else on the record is main-owned and a renderer patch for it is dropped, never merged: `enrollmentStatus`/`enrollmentDetail` (only the enrollment state machine writes them — a forged `enrolled` would skip every consent gate, since `hosts:openShell` and `remote-fs`' `gateHost` key on that field), `hostKeyFingerprint` (the TOFU pin, see below), and `prerequisites`/`enrolledAt`/`lastProbeAt`/`lastProbeOk` (probe output whose `path` values interpolate into remote commands). `managedKey` is never taken from the patch either: it is DERIVED from the path — a pair is managed exactly when `privateKeyPath` sits under `<userData>/hosts/` (`isManagedKeyPath`, `keys.ts`) — because that flag drives the key-deploy step and the delete-time unlink, and a renderer-set `true` over a foreign `~/.ssh/id_ed25519` would have FineVibe delete a key it does not own.

A renderer-supplied `privateKeyPath` is read by MAIN (`ssh-client.connectConfigFor` every connect; `readPublicKeyLine` in key deploy, which ships the public half to the host the renderer chose), so `hosts:create` and `hosts:update` accept only a path inside `<userData>/hosts/` (the managed tree) or `~/.ssh/` (the Browse button's target) — canonical containment via `fs-utils.canonicalPath`, so `..` and a symlink out of the root are refused, and the directory itself never passes (row 34). The chosen gate is containment rather than "ignore the field for non-managed keys": a browsed key path is a supported feature whose value round-trips through the edit form, and ignoring it would leave the same read reachable through `hosts:create`. A path that predates the gate stays usable — a value equal to the stored one passes through untouched, so an existing host with a key elsewhere remains editable.

Fields that matter: `authKind` (`key` | `password`), `managedKey` (FineVibe-generated pair under `<userData>/hosts/<id>/`), `hostKeyFingerprint` (pinned SHA256 — enrollment requires a pin; every later connect re-verifies it, see SSH transport), `prerequisites` (last probe of remote coding-tool binaries), `defaultFolder` (POSIX path, the remote cwd for shells; default `~/.finevibe`), `enrollmentStatus` (`draft` → `probing` → `auth-ok` → `enrolled` | `partial` | `failed`).

## Enrollment lifecycle

`src/main/hosts/enrollment.ts`:

- `testHost` — connect + auth probe. First contact yields `newFingerprint`; the UI must show it and get explicit approval (`hosts:approveHostKey`) before anything is pinned. A pinned key that differs is `hostKeyChanged` — every later connect refuses (hard fail, no TOFU-retry). The handler (`hosts:test`) persists the status machine's `auth-ok` rung when the probe passes on a `draft` record (row 46: the rung had no producer, so a wizard closed after Test & Approve left the host on `draft`); a re-test never demotes an enrolled/partial record.
- Pin grammar (row 32): `hosts:approveHostKey` and `hosts:enroll`'s `opts.pin` take exactly `fingerprintOf()` output — `/^SHA256:[A-Za-z0-9+/]{43}=$/` (`HOST_KEY_PIN`, `hosts-domains.ts`). An empty pin is refused, not stored: ssh-client reads a falsy `hostKeyFingerprint` as "nothing pinned yet", so approving with `''` would silently DISABLE verification for every later connect. Any other malformed string can never be produced by a handshake and would brick the host. `approveHostKey` answers `null` on a refusal (the same shape as an unknown host); `hosts:enroll` drops a malformed pin, which then fails the "host key not pinned" step instead of persisting junk.
- `enrollHost` — requires a pinned fingerprint. Steps: connect → env → key-deploy (managed key: append public key to remote `authorized_keys` via a marker block, idempotent) → prereqs (binary probe) → dirs (`mkdir -p ~/.finevibe ~/.finevibe/run` — the hook sidecar dir; `defaultFolder` is NOT created here (row 46): it is either a folder the user created on the host or the remote home when the record has none, and the Add-project verbs create what they need via `hosts:ensureDir`). A non-POSIX remote shell fails the record (R2: enrollment target is POSIX). Missing binaries land as `partial` with the per-binary report kept in `prerequisites`.
- Status rungs are persisted, not just pushed (row 46): `probing` before the connect, `auth-ok` once auth succeeded, then `enrolled` / `partial` / `failed`. A crashed enroll or a closed wizard therefore leaves the honest last rung on the record.
- `unenrollHost` — rewrites the remote `authorized_keys` removing only FineVibe's marker block, then deletes the managed keypair and keychain entries. Removal is newline-tolerant and remainder-faithful (row 33): an UNTERMINATED block (a deploy truncated mid-write, so the `end` marker never landed) consumes only its begin line plus the one key line the block contract defines — never the keys appended after it — and the untouched lines are re-emitted byte-exact (`\n`-only split, so a CRLF file keeps its `\r`s), with a final newline added only when the kept tail lacks one (the deploy lane appends with `>>`). The file is read through `execCapped`: a copy the exec cap clipped is refused, never rewritten back (row 33 × row 45). Deletion of a host (`hosts:delete`) runs unenroll first for enrolled records (UI-ordered).
- Host hook merge (per-host providers T2) — enrollment merges FineVibe's status-writer hooks into each probed tool's `settings.json` (marker-scoped: every handler command carries `# finevibe-hook`, so merge is idempotent and unenroll strips exactly the block). Foreign keys/hooks survive *content*-identical; when the block changes, the whole file is re-serialized (2-space JSON + trailing newline), so duplicate keys collapse and escapes normalize — byte-identical only on the no-op paths. The `.bak` rule (T3) is the recovery story for a bad rewrite.
- Settings sync (per-host providers T3, UR-5) — push-only local → host for pi/pi-bolt/omp. The bundle builder (`src/main/hosts/settings-bundle.ts`) IS the allowlist: the §4 file-set table per provider (pi: `~/.pi/agent` settings/AGENTS/mcp/skills; pi-bolt adds the npm manifests; omp: agent settings/keybindings + plugin manifests), deduped by path (pi/pi-bolt share the tree), settings.json pushed hook-stripped, every file LF-normalized; `sessions`/`cache`/`node_modules`/`ssh-remote-config.json` never enter a walk. The push (`src/main/hosts/settings-sync.ts`) writes via the provider-fs seam with the one-`.bak`-per-path rule (replaced each sync), `mkdir -p` on the exec lane, records sha256 per pushed file in `HostRecord.settingsSync` (`{providers, lastSyncAt, lastSyncHashes}`), and runs `npm install` on the host for the manifest trees (skipped with a warning when the prereq probe found no node). Drift (remote hash ≠ stored hash) blocks the push until the UI confirms Overwrite (`hosts:syncSettings` with `confirmOverwrite`).
- Remote open/add folder (per-host providers T5, UR-6) — the Add-project modal's verbs on a host live in `src/main/hosts/remote-fs.ts`: `listRemoteDirs` (sftp readdir, dirs-only, 500-entry cap, `fs:listDirs` shape), `statRemotePath`, `ensureRemoteDir` (`mkdir -p` + `printf` echo answering main's canonical absolute path — the same "persist what main answers" rule as local `fs:ensureDirectory`), `cloneRemoteRepo` (the local `detectGitCheckoutUrl` gate verbatim, exists-and-not-empty destination pre-check over sftp, `git clone --` with both words shell-quoted, the local 10-min clone timeout). The file-tree rails (`listRemoteDir` files+dirs 2000-entry cap, `readRemoteFile` size-capped + NUL head-sniff) carry one more gate — `isRemotePathInKnownProject`: the path must sit under a persisted project root of the same host; the dir-browser verbs above stay on the looser T5 gate (the HostRecord is their consent). Path safety is one function: `normalizeRemotePath` accepts only `~`, `~/…` and `/…`, rejects `..` on the RAW segments (a normalized `~/../etc` would silently re-anchor), relatives, bare `~user`, NUL; the renderer never canonicalizes remote paths against the local disk. The gate is host-exists + `enrolled|partial` (`gateHost`, the settings-sync shape) — deliberately NO enumerate-confirm dialog: the local `fs:listDirs` confirm (P1-19) guards a local privacy concept, and on a registry host the consent IS the enrolled `HostRecord` (council R-1, see [security boundaries](security-boundaries.md)).

Status transitions push `hosts:status` events to all windows; the section re-renders from `hosts:list`.

## Secrets

`src/main/hosts/secrets.ts` wraps Electron `safeStorage`. Host passwords are stored under keychain key `<hostId>`, key passphrases under `keypass:<hostId>`. The IPC surface is write-only (`hosts:setSecret`, `hosts:forgetPassword`): no channel ever reads a secret back to the renderer; ssh-client pulls secrets in main only. `hosts:setSecret` refuses an id with no registry record (row 46) — the store is keyed by host id, so an unbounded stale id would leave an orphan ciphertext entry nothing can clear. The in-memory ciphertext cache is LRU-capped (`MAX_CACHED_SECRETS`, module-map-governance allowlist) and the `~/.finevibe/host-secrets.json` file is the source of truth: every mutation is a read-modify-write of the FILE, so eviction can never drop a stored secret (row 46). A failed `safeStorage` probe is re-checked after `SECRET_PROBE_RETRY_MS` (row 100: a keyring that comes up after boot used to lock secret flows out for the process lifetime); a successful one stays cached. `hosts:forgetPassword`/host delete remove the file entry even when storage is unavailable — deletion never decrypts, and gating it orphaned the ciphertext (row 100). The wizard's `secret` field is masked in the UI (`FieldDef.secret` → `type=password`, autofill off) and is never prefilled on edit. `hosts:secretsAvailable` false (Linux without Secret Service) → the UI shows the R1 banner and key-auth-only guidance; enrollment with `password` auth degrades to prompting per session is NOT implemented — password auth without storage is refused.

## SSH transport

`src/main/hosts/ssh-client.ts` (ssh2). Connections are cached per host id in a FIFO-capped `Map` (`MAX_CACHED_CONNECTIONS`, allowlisted in `src/main/module-map-governance.test.ts`); `forceNew` evicts the exact entry, and so does a pin change: a cached connection whose verified pin no longer matches the record's `hostKeyFingerprint` — including one established through an explicit `verifyHostKey`, which is never labeled pin-verified — is replaced on the next connect (old client closed). `hostVerifier` compares the server key against the pinned fingerprint and refuses on mismatch — every connect, not only enrollment/test; a refusal surfaces as `host-key-changed` and is recovered via Test & Approve in Settings → Hosts. Shell/PTY traffic for enrolled hosts goes through `spawnShellPty` (`src/main/pty-manager.ts`) spawning the local `ssh -tt -p <port> user@host` binary — the xterm pane and pty:data/pty:exit contract are unchanged; the renderer opens such a tab with `openRemoteShellTab` (`src/renderer/components/project-terminal.ts`), which Phase 1 scopes to the active project's terminal panel. `exec()` output is bounded: stdout is kept up to `MAX_EXEC_OUTPUT_BYTES` and the rest of the stream is drained and dropped (row 45 — the lane was unbounded while enrollment documented a cap). Callers that re-persist what they read use `execCapped()`, which returns `{ out, truncated }` so a clipped copy can be refused instead of written back. A record update evicts the cached connection too (row 44): `updateHost` compares the merged record against the stored one and calls `closeConnection` when an identity field actually changed (`CONNECTION_IDENTITY_FIELDS` in `host-registry.ts`: host, port, user, authKind, managedKey, privateKeyPath) — the pin gate above covers fingerprint rotation, this covers endpoint and credential swaps, and main-side status/probe writes touch none of those fields, so they keep the connection warm.

## Limits

Host name ≤ 64 chars; port 1-65535 (default 22); one password + one keypass per host; connection cache `MAX_CACHED_CONNECTIONS` and exec output ceiling `MAX_EXEC_OUTPUT_BYTES` (both exported from `ssh-client.ts`); secret cache `MAX_CACHED_SECRETS` + failed-keyring retry window `SECRET_PROBE_RETRY_MS` (exported from `secrets.ts`). `defaultFolder` must be a POSIX path (a Windows target path is dropped at validation; Windows targets are R2).

## IPC surface

`hosts:list` `create` `update` `delete` `openShell` `secretsAvailable` `generateKey` `setSecret` `forgetPassword` `test` `approveHostKey` `enroll` `unenroll` `syncSettings` `listDirs` `stat` `ensureDir` `cloneRepo`, plus the pushed `hosts:status` (last-sync metadata and the drift list ride that push — there is no pull channel). Secrets cross only into main. `hosts:openShell` requires an enrolled record and a fresh `sessionId` owned by the renderer shell pane. `hosts:syncSettings(hostId, providerIds, confirmOverwrite?)` takes ids only — the file set, the local reads, and every remote write are main-side (T3); `hosts:syncStatus(hostId)` reports last-sync metadata + the drift list. The T5 lanes (`listDirs`/`stat`/`ensureDir`/`cloneRepo`) take a host id + strings only; `remote-fs.ts` owns normalization, the gate, argv and quoting. The file-tree rails (`fs:listDir`/`readFile`/`stat`/`exists`/`isDirectory`) take a trailing optional `hostId` (parent plan §11): set to a registry host, each routes over sftp through `remote-fs.ts` — gate `enrolled|partial` + path safety + `isRemotePathInKnownProject` (the path must sit under a persisted project root of the same host, the remote twin of the local read gate); absent/`local` rides the unchanged local rails. Remote watching (Phase 4) polls instead of inotify: `src/main/hosts/remote-watch.ts` re-reads each watched remote directory on a 5 s interval (`REMOTE_POLL_MS`, `MAX_REMOTE_WATCHES` 200 FIFO) and emits the entry-set delta on the same `fs:changed` channel the local watcher uses, so the tree and reader subscribe once; paths that are not watched refresh on expand and panel re-render, and a preview reloads on reopen.
