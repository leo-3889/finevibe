# Session lifecycle

Terminal keyboard input tracks the CLI's DEC private mode 9001 requests. Once ANY win32-input key record has been written to a ConPTY-backed PTY, ConPTY's input parser is armed for the lifetime of that PTY and silently discards every later bare ESC byte — plain CSI and further records keep flowing, so the visible symptom is "arrows work, Escape dead" (Escape-to-close in TUI menus like `/model` stops reaching the app). Mode 9001 is therefore monotonic per PTY: `?9001l` is informational only, never a licence to resume bare-ESC writes. ConPTY advertises `?9001h` as the very first output bytes of every fresh PTY, so local Windows panes (session terminals, the project shell) latch at creation (`latched`); read-write remote panes latch only on a real `?9001h` sighting relayed from the host through `writeRemoteData`, keyed by session id (`latchKey`), since the host OS is unknown. The latch lives in module-level state keyed per PTY, so a handler attached to an already-armed PTY (pane re-render, app reload, re-attach) starts encoded and cursor/navigation keys and Escape keep going out as Windows key records, preserving modifiers — avoiding ConPTY turning OMP arrow sequences into literal prompt characters and swallowing bare ESC. When mode 9001 was never sighted, xterm handles the keys normally. `win32-terminal-keys.ts` owns this adapter. Select-only settings dialogs take keyboard focus from the terminal when opened.

The creation-time pre-arm assumes node-pty's ConPTY backend, its default on Windows. The winpty fallback (reachable only through `CONPTY_DISABLE`) has no win32-input parser, so a record written there reaches the child verbatim — it never delivered a bare ESC either, so Escape was already dead on that backend.

Mouse modes do not survive ConPTY in the other direction: ConPTY parses an app's `?1000h`/`?1002h`/`?1006h` into console mouse mode and re-emits only what a legacy console app asked for, so a VT-native CLI's mouse modes never reach xterm (verified on a pi-bolt PTY stream — `?1049h`, `?1004h`, `?2026h` pass, the mouse modes do not). With no wheel reporting bound, xterm's alt-screen fallback sends an Up/Down arrow per notch, which the CLI reads as prompt-history browsing: the input line cycles and the transcript stays put. `terminal-wheel-scroll.ts` writes the SGR wheel report the terminal would have sent, only while the pane is in the alternate buffer with `modes.mouseTrackingMode === 'none'`; panes where the modes do arrive (Linux/macOS local, SSH) and Ctrl/Cmd/Shift+wheel stay with xterm, so Shift+wheel remains native scrollback.

Hook inspector event ingestion is incremental: each turn reads at most 64 KiB, preserves partial JSONL records and UTF-8 bytes, and schedules further backlog reads. Individual records over 64 KiB are skipped. Renderer retention is bounded by both 2,000 events and 2 Mi characters per session. Closing a session cancels pending ingestion continuations and releases its reader state.

Pi/OMP launches use exclusive session directories — `%APPDATA%\FineVibe\omp-sessions\<uiSessionId>` (Pi: `pi-sessions`), created by `src/main/launch-session-dir.ts` and passed as `--session-dir`. Transcripts therefore never enter the CLI default store (`~/.omp/agent/sessions`), so sessions launched in FineVibe are invisible to the CLI's default-store resume picker; resume inside the tab's history or pass the launch dir. Provider search scans the per-launch dirs under userData. Discovery shares registration generations per watched directory rather than duplicating complete filename snapshots for each session. Registration still forces a fresh synchronous listing (`src/main/pi-compatible-session-watcher.ts:309`). During polling, a cached listing is reused while the directory mtime is unchanged and no watched rename has dirtied it, and a listing older than 30 s is refetched by the next scan (`:151`) — that cache lifetime is the safety net for missed notifications; there is no reconciliation timer of its own. Two-second polling still checks for changes (`POLL_INTERVAL_MS` `:130`, timer `:396`). Existing-file exclusion remains in force. One native `fs.watch` per launch directory is shared by every session registered for it, a re-spawn reusing the same dir included (`watchDir` `:399`); every watcher carries an `'error'` handler that logs once, closes the watcher and releases its slot, leaving the poll as the correctness path, so `EMFILE` or a detached volume cannot throw out of the watcher and take main — and every PTY with it — down (`:413`). The watcher, that directory's registration history and its listing cache are released when the last session registered for the directory unregisters (`:332`), and `stop()` closes every watcher and clears all watcher state (`:428`). Closed tabs no longer keep their launch dirs forever: `pruneLaunchSessionDirs` deletes a launch dir only when EVERY timestamp it exposes (sidecar `createdAt`, newest `*.jsonl` mtime, the dir's own mtime) is past `LAUNCH_SESSION_RETENTION_MS = 30 days` (`src/main/launch-session-dir.ts:71,104-183`, age rule `:150-183`), never treating an unknown age as expired; entries are `lstat`'ed so a symlinked dir is skipped, every removal path is `base` + one readdir name, at most `PRUNE_SCAN_LIMIT = 200` entries are examined per pass (`:78,152-153`) — on an over-limit base the names are ordered by dir mtime ascending first (`oldestDirsFirst` `:184`), so the prune examines the oldest dirs before the cap and a >200-dir base can no longer strand expired dirs in the unexamined tail — and the sweep runs at most once per base per process, triggered from `ensureLaunchSessionDir` (`:88,91,112`).

Codex CLI has no hook that reliably reports its session ID. The fallback watcher attributes new rollout files (`~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<id>.jsonl[.zst]`) to the tabs that launched Codex, keyed by cwd: `registerPendingCodexSession` records the launch cwd, and a rollout is assigned only to a tab registered for the cwd carried in the rollout's `session_meta` line. Attribution used to be a global FIFO over the shared `~/.codex/history.jsonl`, so any external `codex` run (terminal, CI) hijacked the oldest pending tab with a foreign transcript and a wrong resume target. Within a cwd, pairing is oldest pending tab ↔ oldest rollout: day directories are read oldest-file-first and pending tabs are matched in registration order, because descending file order paired the oldest tab with the newest rollout — two Codex tabs in one repo launched within one scan window swapped transcripts, titles and resume targets. A rollout whose meta line has not landed falls back to the session id in the filename and is adopted only when exactly one tab is pending; with several, the watcher stays hands-off. A failed `writeCliSessionId` (EMFILE/ENOSPC/EACCES — the write runs inside the 2 s poll and the 500 ms watch debounce, and `src/main` has no `uncaughtException` handler) leaves the tab pending and the id unclaimed, so the next scan retries: no lost claim. Each scan walks the zero-padded `YYYY/MM/DD` tree newest-first and prunes day/month/year directories whose NAME predates the oldest registration, keeping cost O(recent days) no matter how much Codex history exists. Parsed `session_meta` is cached per path keyed by `(mtimeMs, size)` with FIFO eviction at `MAX_META_CACHE_ENTRIES = 256`, and a `.jsonl.zst` rollout larger than `MAX_COMPRESSED_META_FILE_BYTES = 8 MiB` is skipped for meta — without these, every scan re-read and fully decompressed (≈10× the compressed size) every rollout in today's directory for the life of a pending tab. `stopCodexSessionWatcher()` closes the recursive watch, the poll, and the debounce timer and clears all watcher state; `codex-provider.cleanup()` calls it, so a scan armed inside the debounce window cannot fire after quit and recreate `os.tmpdir()/finevibe` (Pi/OMP watchers do the same in their `cleanup()`).

The renderer owns session records in `src/renderer/state.ts`; the main process owns PTYs. A non-shell CLI PTY exit destroys and removes its live session. `src/main/ipc-handlers.ts` owns replacement cleanup. A `killPty` that arrives while `spawnPty` is still awaiting records a pending kill that the spawn consumes immediately after registering the PTY, so the CLI tears itself down instead of orphaning; every spawn path that returns without spawning clears the marker so a stale kill cannot hit a later re-spawn of the same id. A rejected launch (a `LaunchSpecError` from `resolveLaunchSpec`, e.g. unsupported extra-arg flags, or Claude keychain isolation on an unsupported platform) never throws into the IPC caller: the renderer fires `pty:create` without awaiting, so a rejection would be a swallowed promise leaving a blank pane. The message is painted into the pane through the existing `onData` callback and the failure is reported on the existing `pty:exit` channel as `onExit(1)` carrying the `SPAWN_REJECTED_EXIT_REASON` sentinel (`src/shared/constants.ts`): the renderer learns no PTY ever existed, keeps the pane open so the actionable "remove these options" message stays readable, and skips the transcript exit-reason read a real exit performs; any pending kill recorded for the id is cleared (`src/main/pty-manager.ts spawnPty`). The UI distinguishes active sessions, archived resumable sessions and history entries. State is saved to `~/.finevibe/state.json` through an atomic temporary-file rename: the payload is written to `state.json.tmp` by a loop that keeps writing until every byte is out and aborts (never renaming) if the descriptor stalls, then `fsync`s, then renames, so a partial temp file can never replace a good `state.json` (`src/main/store.ts:394-436`). `saveState` itself is a leading-edge throttle, not a pure debounce: the first save of a burst writes through immediately and mutations inside the following 300 ms coalesce into one trailing write of the LATEST state (`store.ts:125-163`), so a crash loses only what arrived after the last disk write. The quit-path guarantee is main's `before-quit` `flushState()`, which disarms that pending trailing write and then synchronously writes the last state payload main received; an armed timer left alive would fire after teardown and write `state.json` a second time while the app-data directory is being torn down (Windows logout / roaming profile), surfacing the write error as an unhandled exception in the timer (`store.ts:357-370`). Renderer persist is a leading-edge throttle: the first mutation writes immediately, mutations in the following 200 ms coalesce into one trailing save, and `beforeunload` flushes an armed save (`ffcd283`) — on the `app.quit()` path that flush lands after `flushState()` and enters the store's 300 ms window, so it guarantees renderer-only unloads (reload) only; a mutation newer than the last payload main received is lost on quit. Startup recovery parses both `state.json` and its `state.json.tmp` sibling and keeps the one with the newer mtime (coarse-mtime ties keep `state.json`): the atomic write fsyncs the temp file before the rename, so a crash with the data durable and the rename not yet durable leaves the newest snapshot in `.tmp`, which the first plain save would otherwise truncate. A parsed `.tmp` is always deleted, even when it loses to `state.json`, because a stale copy left behind is what a later corrupt `state.json` would resurrect. `preferences` is normalized exactly once by the loader — `loadState()` returns `LoadedState`, where `preferences` is guaranteed present via the single `DEFAULT_PREFERENCES` default (`store.ts:39-53,106`), and every writer (`saveState`, `saveStateSync`) normalizes the cache the same way (`store.ts:142,380`), so main-side consumers never guard the field; keep the default in sync with the renderer's `defaultPreferences`. `loadState()` caches its parsed result in-process (the `fs:*` guards and the synchronous startup-prefs channel call it on hot paths) and every save updates the cache; `invalidateStateCache()` drops it and is a test seam, not a runtime API.

Session history tracks CLI sessions from creation: `commitNewSession` records an `active` row (keyed by the live session id) as soon as a CLI tab spawns, so the history panel reflects opens immediately, including sessions that are closed without a prompt. The discovered `cliSessionId` mirrors onto that row; closing finalizes it in place (name, cost, `closedAt`, exit info, `transcriptAvailable`). A `/clear` archive appends a separate closed row for the cleared conversation and never touches the live row. Active rows are exempt from the 500-entry cap, survive Clear History (with bookmarks), and clicking one activates its tab — a live session is never "resumed", which would duplicate it on the same CLI transcript. Renaming a live tab renames its own row; closed rows are immutable history. On state load, rows whose tab did not survive are finalized (closed at load time).

History export lives in `src/main/session-export.ts` and the history context menu. `Export session (zip)` writes `meta.json` (the history entry plus resume coordinates), the provider-native transcript verbatim under `transcript/` when it resolves, readable hook sidecars from `STATUS_DIR` under `sidecars/` when present, and a README. `Export transcript (single file)` copies the transcript verbatim (falling back to `meta.json` when absent). Transcript resolution goes through `provider.getTranscriptPath(cliSessionId, projectPath, configDir, sessionDir)`, passing the exclusive Pi/OMP launch directory whenever the row carries a live session id; transcript-existence checks use the same rule. Imports are not wired — exports are reference snapshots. Zip generation rejects on a stream error from either side: `pipe()` returns the destination, so a source-side failure (the transcript being removed mid-export, e.g. Codex compacting `.jsonl` into `.jsonl.zst` while the user sits in the save dialog) is caught explicitly instead of surfacing as an unhandled `'error'` event that would crash main. A half-written archive is never left behind: the destination stream is `destroy()`ed and awaited to `finished` BEFORE the partial file is unlinked, because `pipe()` leaves the destination open when the source errors and on Windows `unlink()` of a file with an open write handle fails with EPERM — cleanup ordered before the handle closed left the untrusted partial archive on exactly the platform the IDE ships to.

Session activity changes on provider hook or transcript events. A completed event moves a linked Kanban task to Done. A `completed` while the session still has children running is held as `working`: `session-activity.ts` counts in-flight subagents from the pushed `subagent_start` / `subagent_stop` inspector events (`noteInspectorEvents`, fed by `index.ts`) and releases the held completion when the last child stops, so no surface shows the completed glyph (or auto-Dones the task) mid-flight. Providers without an inspector event stream (Pi / Pi-Bolt / OMP transcripts) are covered on the source side instead: the transcript poll reports `working` while the `pi-subagents` extension has a run `queued`/`running` for that transcript (`src/main/pi-subagent-runs.ts`), so `completed` reaches the renderer only once the last child is done. Closing or losing an unfinished session only clears its live `sessionId`; it does not complete the task. A cancelled Pi/OMP turn (`stopReason: "aborted"`) reports `waiting`, never `completed`, mirroring Claude's `StopFailure`, so interrupting a turn does not mark its Kanban task Done. `board-session-sync.ts` resolves the owning project even while another project is selected.

An abnormal CLI exit is annotated: Pi/OMP can supply a fatal or signal reason through a trailing `session_exit` entry even when the process exits with code 0. The lookup checks the provider's transcript path if the watcher has not resolved one yet and ignores an exit marker older than the current launch (`src/main/ipc-handlers.ts:662-668` fallback, timestamp gate `:677-680`). The read itself is bounded: 16 KiB of tail, retried once at the 4 MiB cap when that window contains no complete line, and the marker is accepted only across crash-flush appends (`tool_execution_start` / `toolResult`, at most 32 of them) — a real user/assistant entry after the marker ends the scan, because the CLI resumed that transcript and the marker is history (`src/main/providers/pi-compatible-transcripts.ts:285-322,330-342`). A marker whose `kind` is `normal` or whose reason is `dispose` is discarded in favour of the process result (`src/main/ipc-handlers.ts` `describePtyExit`:112-123). Otherwise the process exit code or signal supplies the reason. Crash history retains PID, code and signal, and offers Resume when a transcript exists. A user-initiated close removes the session before its PTY exit arrives, so it is not reported as a crash.

Numbered default names come from `src/renderer/state/session-naming.ts`. Group names follow the same all-locale numbered pattern (`tab.group.defaultName`); closing a session prunes its group's membership and a group below two members dissolves (`src/renderer/state/tab-group-state.ts`). Live provider titles are adopted by `src/renderer/session-title.ts` when automatic titles are enabled and the user has not renamed the session. There is no main-process one-shot naming service or fifth-prompt title pass. A transcript-polled title (Pi/Pi-Bolt/OMP) is only mirrored while a live PTY drives `session-transcript-sync`; a title generated or changed while FineVibe was closed would otherwise be lost on re-open, so after state load the renderer sends every restored self-titling session to `session:syncRestored`, which re-registers title-only transcript sync (never status, to avoid reviving a stale status on a dead tab) and mirrors the title only for a session whose `cliSessionId` is already known. Pi-lineage titles are `session_info` entry names (`--name` / `/name` / `pi.setSessionName()`), read from the tail window first (recent renames land at the end of the append-only file) then the head; a name buried mid-file is invisible to the bounded windows until they cover it — the CLI's own picker reads the whole file, a mirror cannot. A session whose id was never persisted stays unresolved — ownership is not inferred from cwd + creation time, which can assign an unrelated conversation and persist it. A resumed session re-registers without the title-only flag and resumes full title/status mirroring; a restored tab closed without a resume releases its title-only entry via `session:release`. The legacy SSH launch setting `SessionRecord.sshHost` (free text, validated by `src/shared/ssh-host.ts`) is retired: at every load boundary `migrateLegacySessionSshHosts` adopts the registry `hostId` for sessions tagged with a registered hostname (unique match), and unregistered/ambiguous values keep `sshHost` for the legacy `pty:create` wrap — one release carrying both spellings (parent §11). The tab context menu is a registry picker writing `hostId` (`setSessionHost`); a registry-host session (Phase 2) is keyed by `SessionRecord.hostId` on both sides — the PTY is the `ssh -tt -p <port>` wrap (see [provider contracts](provider-contracts.md)), and everything that reads the session off-box reads it through the provider-fs seam. Status: the on-host hooks merged at enrollment write `~/.finevibe/run/<sid>.status` on the host; `hook-status.ts` polls those sidecars on a sweep of its OWN in-flight flag (a slow sftp round trip never blocks the local fs poll, audit T2 #2), each read a bounded 4 KiB tail, and a failed host read coasts that host for `REMOTE_HOST_COOLDOWN_MS` = 30 s (map capped at `REMOTE_HOST_COOLDOWN_MAX` = 32) so a down host costs one connect timeout, not one per session per tick. Title/transcript sync registers with the session's `hostId` and consumes paged windows over the seam (head 8 KiB, tail 16 KiB, seam cap 1 MiB), never whole files, one in-flight remote read per entry, keyed by the same (mtime, size) gate as the local path. The host-side launch dir and session-id env are derived once (`remoteLaunchSessionDir`, `remoteEnvPrefix`) so spawn argv and transcript resolution can never disagree, and the derivation is home-relative — a Windows controller launches and reads POSIX paths it never canonicalizes against its own disk.

`src/main/file-watcher.ts` watches file-tree and reader directories lazily, including the parent directory to survive atomic replacement. `src/main/git-watcher.ts` watches Git state separately, using recursive watching on Windows/macOS and capped per-directory watching on Linux. Hook `.events` reading advances its byte offset by bytes actually read, retains incomplete line bytes separately, and emits only complete parsed records. A size smaller than the offset resets the reader. The hook-status `fs.watch` carries an `'error'` handler that closes the watcher and schedules one restart five seconds later, so `EMFILE` or a volume unmount cannot crash the main process and take every PTY with it. POSIX status hook commands write `.status` atomically: `statusCmd` (`src/main/hook-commands.ts`) echoes to `<sid>.status.tmp` and `mv`s it into place inside `STATUS_DIR`, because a `>` redirect truncates the target before writing and on a coarse-mtime filesystem (1 s tmpfs, HFS+) the truncate shares the final write's mtime tick — the hook-status poll re-reads a status file only when its mtime CHANGES and validates the content against the 4-value allowlist (`working`/`waiting`/`completed`/`input`), so a reader that sampled a mid-write file records the truncate's mtime, rejects the partial content, and never re-reads the completed value: the transition is dropped forever. The temp name `.status.tmp` matches no `KNOWN_EXTENSIONS` entry in `src/main/hook-status.ts`, so the poll skips it, `extractSessionId` maps it to nothing, and cleanup ignores it. The Windows branch keeps the Python `status_writer.py` (truncate-then-write): NTFS mtime (100 ns) is far below the 2 s poll cadence, so that lost-update window is a POSIX hazard. Python helper scripts are installed into `SCRIPT_DIR` (`~/.finevibe/run`) and are deliberately kept on exit — deleting them races CLI processes that outlive the app, and they are reinstalled on launch; only status DATA files in `STATUS_DIR` (`os.tmpdir()/finevibe`) are cleaned. See [performance and resource limits](performance.md) for exact bounds and oversized-record handling.
